# Security

JoinAllworld is early software. This page describes what the code does and where its limits are, so you can decide whether it fits your use. Nothing here is a guarantee, and the project has not had an independent security audit.

## Reporting a vulnerability

Please report privately rather than in a public issue.

- If the repository's **Security** tab offers **Report a vulnerability**, use it.
- If it does not, open an issue that says only that you have a security report and ask a maintainer for a private channel. Do not include details, proof-of-concept code or affected data in the issue.

There is no bug bounty and no guaranteed response time. Only the latest `main` is supported.

## Device sessions are not accounts

- A session is a random secret stored in an `HttpOnly`, `SameSite=Lax` cookie, plus a nickname of 3–24 characters. Over HTTPS the cookie is named `__Host-sid`, which a sibling host of the same site cannot set; a cookie under the earlier name `sid` is still accepted for a guest's own session, and the next answer also sets it under the new name (the old cookie is kept beside it for this release, so that the previous build would still know every guest; `__Host-sid` wins when both are present). A device session has no password, e-mail address or verification, and does not authenticate a person. **Accounts are a separate, optional layer that is off unless configured** — see [Accounts](#accounts-off-unless-configured) below.
- **Anyone who obtains the cookie is that device.** The secret is never sent to other players: presence, chat and voice signalling use a separate public ID.
- Nicknames are not unique or reserved. A name is not proof of identity.
- **Sessions expire.** The default lifetime is 30 days (`SESSION_TTL_DAYS`), renewed on authenticated use. Open connections are closed when the session expires.
- **There is no recovery.** Authenticated use renews the device session for 30 days. If the cookie is cleared, lost or expired, a browser with a cached life shows an explicit choice before creating a separate new identity. The old life is moved to an archive in the server's data file so it is not destroyed, but no endpoint or tool restores it, and players cannot retrieve it themselves. Do not treat progress as durable. A session that expires without ever having finished character creation has no life to keep and is deleted rather than archived.
- Sessions created before the public ID was introduced are archived the same way at server start, so those devices start fresh.
- The cookie is marked `Secure` only when the server itself receives TLS, or when `TRUST_PROXY=1` is set and the proxy sends `X-Forwarded-Proto: https`. Serve over HTTPS.

## Accounts (off unless configured)

Design, threat list and open questions: [docs/ACCOUNTS.md](docs/ACCOUNTS.md). **This feature has not had an independent review; have it reviewed before enabling it on a public server.** With `ACCOUNTS_FIREBASE_PROJECT_ID` and `ACCOUNTS_FIREBASE_API_KEY` unset nothing below exists: no sign-in is shown, nothing is stored and no request is made to a provider.

- **Who a person is comes from a signed ID token only.** The browser signs in with the identity provider (Google, or an e-mail address and password) and hands the server a short-lived ID token. The server verifies it itself on both hosts: RS256 signature against the provider's published keys, audience and issuer of the configured project, expiry, an age of at most five minutes, a sign-in at most an hour old, and a confirmed e-mail address. A uid, an address or a "verified" flag sent beside the token is never read. A token is accepted once.
- **The game never sees or stores a password,** and stores no ID token or refresh token. It stores, per account: the provider's subject id, the confirmed address (shown to its owner; used for nothing else), how the person signed in, and two times. The audit trail records events without a token, address, subject id or cookie.
- **Signing in always issues a new cookie** (same attributes as the device cookie). A cookie presented at sign-in is never kept, so a planted cookie gains nothing. A signed-in browser's cookie is a *device binding*, honoured over HTTPS only under the name `__Host-sid`; the account's character is stored under a key that is never sent to a browser and is refused if presented as a cookie. A binding lasts 30 days from its last use and at most 90 days.
- **A binding alone plays the character and signs itself out.** Ending other devices' sign-ins, downloading the account's data, switching character and deleting the account each also need a fresh ID token for the same account.
- **When the owner arrives, earlier sign-ins end**: a sign-in that links a character into an account that already existed, or that uses another way of signing in than the account last did, removes every other binding. The number of signed-in devices is shown after signing in and in Settings.
- **Account state changes** require an `Origin` header naming this host, scheme included (the general rule lets a request with no `Origin` through; these routes do not) and, when a session cookie is presented, an anti-forgery token derived from that cookie.
- **Sign out** ends this browser's binding and still works if accounts are later switched off; sockets of an ended binding are closed.
- **No answer says whether an address has an account**: every refused token is one answer, and a password-reset request is answered the same way, before the provider has replied. What the provider itself reveals to someone who asks it directly depends on the provider project's settings (turn on its e-mail enumeration protection).
- **Limits** on tokens and resets are per address, per account and per address written to; the server-wide sign-in bucket counts only tokens that verified and whose address is confirmed. Limiter rows are bounded per class of key and a full table makes room rather than refusing new keys, so a flood cannot lock other visitors out. On the Node host limits are in memory and reset on restart.
- **A new account is sent one welcome e-mail** to its confirmed address when the mailer is configured (no tracking, sent once, never to a guest or an unconfirmed address).
- **Signing in never destroys a life.** A played life that cannot be the active character is set aside in the archive, marked with the account that may bring it back.
- **Limits of this design:** an ID token stolen in the minutes before it is used can be used once from elsewhere; a password reset by itself does not end other sign-ins (the provider's token does not say a password changed); a copy of the data file contains valid cookie values (for device bindings as for sessions); erasing a character does not erase what other features hold under its public id; there is no second factor. The provider is a dependency and knows who signs in.

## Game state

- Cash, needs, location and the action in progress are changed only on the server and advanced by server time. The client displays state and cannot set it.
- When the server is unreachable the client is read-only; it does not apply or queue actions locally.
- Each action carries an ID made by the client from the time and a random UUID. A repeat of the same ID returns the recorded outcome, reuse of an ID with different contents is rejected, and IDs older than 24 hours (or more than 30 seconds ahead of the server) are refused without being run. The receipt is kept for those 24 hours in the player's session and is never dropped earlier; a session holding 10,000 unexpired action receipts is refused further actions (429) until old ones expire.
- **Server-only actions.** Some actions are one half of a change whose other half is shared storage (a ballot, an ad slot, a gift between two players, city news). They are declared `serverOnly` in the rules engine and are refused with `server_only` unless the server itself runs them inside the store transaction that writes the other half. The public `POST /api/action` never carries that authority, whatever the request body contains.
- **Requests that move money or create something are applied once per request id — and that is all an id promises.** A gift, a player interaction, a new group, a radio shout-out, an ad rental, standing for Governor and a problem report each need an id of the same form (`<unix ms>:<uuid>`); without one the request is refused (400) before anything is charged or filed. All seven go through one helper (`server/routes/once.ts`), as does anything a server module spends through the rules engine:
  - the same id again returns the first outcome and changes nothing; the same id with different contents is refused (409);
  - an id older than 24 hours is refused as expired (409) and never run, which is what makes it safe to drop its receipt after 24 hours;
  - a receipt is **never** evicted before that. Capacity is bounded by refusing instead: a player holding 2,000 unexpired receipts gets 429, and with 200,000 on the server everyone gets 503 — both before anything is charged, both saying to try again later;
  - player interactions (no money moves) and everything else are counted separately, each with those limits, so a flood of interactions cannot stop a gift or a paid request, nor the reverse;
  - the receipt is written to the data file in the same transaction as the change it records, so it survives a restart.
  
  What an id does **not** give: it is chosen by the client, so it proves nothing about who sent a request or when, and the same operation sent under a *new* id is a second operation. Those are bounded by each feature's own limits (three gifts and ₦10,000 a day — except money an admin credited, which the owner decided has no gift limits: see docs/ADMIN.md, "Unrestricted funds" — three shout-outs a day, one candidacy a week, one owner per ad slot), not by ids. A vote, a friend request, a knock and a Bae request need no id: the stored ballot, friendship, knock or request is itself the record, and repeating one changes nothing. A message is stored once per client id for as long as it is among its conversation's last 200 messages, and a replay is answered only to someone still in that conversation. The gem prize is an ordinary action and is paid once a day.
- **Where a gift lands.** In the recipient's life in the city it was sent from, if they have one there; otherwise in the life they played most recently. A gift is never credited to a life that does not exist and never creates one: if the recipient has no life anywhere it is refused before the sender is charged. A gift waiting for an offline recipient is kept until they next play and returns to the sender after seven days; it is never dropped while either player still exists on the server.
- **A life whose quick start is not confirmed is not in the city.** A new session's life is held until its look has been confirmed by the server (one action, sent when the player taps Play). Until then it accepts nothing else, cannot join any room, is not registered for messages or search, and is in no directory, list or counter; a session that never gets that far is deleted when it expires, not archived.
- **A guest is exactly a device session.** After Play the life is a *guest*: the same cookie session as before, playing in public venues, with no traits, home, rent or loan until the player settles in. Nothing was added to authenticate a guest and nothing is needed to "save" one — settling in is a set of game actions on the same session, each validated by the server in order. The server refuses every home-only action for a guest (going Home, furniture, groceries, moving house) and every `estate.*` action (taking or changing a local government, styling, upgrading or moving into a house), so the states the economy assumes — a house, the loan, the furnished room — exist only once the player has settled in, which happens exactly once per life.
- **A guest has no place in the city.** A guest has no local government and no house: the server allocates no plot to it (not even through its own server-only `estate.assign`), and it is in no residents directory, no local government's listing, no estate, no rich list and no resident counter. It is listed as a person in the room of the public venue it stands in, like anyone there, and nowhere else. Missions are not dealt, counted or payable until it settles in.
- **Where you live is chosen, never located.** Settling in takes the id of one of the twenty local governments in the action itself (`onboarding.home { lga, via }`). "Find my local government" asks the browser for a position, works out the local government **on the device** from boxes bundled with the map, and keeps only the id the player then confirms; the position is a local variable of one function and is never sent, stored, logged or put in an analytics event. The server validates the id against its list, allocates a plot there and records it in the life; the house is free, so settling in moves no money beyond the start cash the birth lottery already set. A test asserts that the module reads the coordinates in exactly one place and names no network or storage API.
- **Deliveries from the server reach a life that is still being created; nothing else does.** While a new life is held for its look, every action is refused — except three server-only actions that deliver something *to* it and that no player can send: a gift, friendship or other social effect from another player (`social.server`), a referral gift (`growth.referral`) and a finished table game (`growth.table-result`). Each still runs under its own rules and caps, inside the store transaction that records why. Every other server-only action (a vote, a candidacy, an ad rental, a shout-out, city news, a plot assignment) stays refused for such a life, and the server's authority never unlocks an ordinary player action.
- **One landing for a link, and what it trusts.** A link may carry `join=<public id>`, `ref=<share code>` and `table=<table id>`. The browser reads them by shape only (a UUID, 8–16 lowercase letters and digits, a short id) and keeps them on the device until each is answered; none is a credential and none is trusted: the server looks the code up in its own share table, validates the public id, and a table id only selects a table that exists. The referral a code attaches pays nobody until the newcomer has been paid for work on real Lagos days (see "Growth features").
- **The invite landing discloses no more than the house link already did.** `POST /api/social/join` (what `/v/<public id>` and `?join=<public id>` call for a new visitor) answers the inviter's name and whether they are at home, out, reconnecting or offline — what `GET /api/social/house/:host` already tells anyone holding the link. The venue is answered only when the caller is put in it or already stands in it. Being put there is free and is limited to one time per life, to a guest, in the life's first ten minutes; the venue is read from the inviter's own venue-room connection, never from the request, and the action that moves the guest cannot be sent by a player. A blocked pair is answered as an unknown player.
- **What "saved" means.** An action, message, gift, purchase, vote or report is answered only after the write of the data file that contains it has been renamed into place. A poll (`GET /api/life`) whose settlement produced an outcome — cash moved, a timed action finished, the player arrived, an illness, skill, goal or roadside event changed — is saved before it is answered too. A poll that only moved the clock is answered from memory and written within one second; if the process dies first, that settlement is computed again from the stored state. "In the file" means written and renamed. It survives a crash of the server process. Writes are **not** `fsync`ed, so a power cut or a kernel crash can lose the most recent writes even though they were acknowledged.
- **What a failed write means.** If the data file cannot be written (a full disk, a removed directory), every change that is not yet in the file is undone in the server's memory — the requests whose write failed, and any that had been applied on top of them — and each of those requests is answered `503 storage_unavailable`. A request that was answered with that error changed nothing: not in memory, not in the file, not later. The server does not retry in the background. The client retries; the same action or request id is then applied once. While writes fail, reads still work and every successful answer carries `"storage": "failing"`; the block list, the mute list and room admission are only ever updated from changes that reached the file. The server cannot save anything in that state, so treat it as read-only until the disk is fixed.
- **Leaving a venue ends room membership, and only a saved departure does.** One rule decides who is in a venue (`canOccupyVenue` in `server/protocol.ts`): recorded there and not on the way out — a trip, the automatic commute, any timed action that moves the player. When a life departs, that player's sockets are marked at once and forward nothing (no chat, movement, voice state or signalling), and the room is then re-checked against the life **in the data file**: if the departure was saved the membership and the voice flag end; if its write failed the departure did not happen and the player stays. The server re-checks a player's rooms after every API request they make while they have a socket in a room, whether it succeeded, was refused or could not be saved. If the store cannot be read at all, the sockets concerned are dropped. These are protocol-level statements about the Node server: membership, the voice *flag* and signalling. They say nothing about audio.
- **Random outcomes are not chosen by the client.** Each life has a salt made on the server from the platform's cryptographic random source, stored beside the life and never sent. Every roll for a stored life is seeded from the action id (or the settlement times) keyed with that salt, so a client that runs the same rules cannot pick an id for the roll it wants; the same id replayed is answered from its receipt. A state that did not come from the server's own settlement has no salt and rolls from the platform's random source, never from the id alone.
- **Only the server's own save can settle money at load.** If a saved timed action can no longer run (its definition changed, its venue is gone), the server refunds what was charged at its start, or charges a metered activity for the time used, once, when it loads its own stored life. The same data from anywhere else — the browser's cached copy, anything imported — is only cleaned up: no money moves.
- **The wallet explains itself.** Every cash change is a ledger line with a reason and a time. The statement (`GET /api/support/statement`, Phone → Statement) gives opening balance, every kept change, closing balance and whether the arithmetic holds. If a stored balance ever disagrees with its own history, the server adds a visible "Balance correction" line instead of leaving the difference unexplained.
- **Earning is bounded.** Each repeatable source of money has a daily cap or a cost: one paid career shift per Lagos day, eight paid gigs per Lagos day, one gem prize, one found wallet, capped deposit interest, capped gifts. `src/game/economy.test.ts` and `src/game/conservation.test.ts` check that cash always equals what the life started with plus the sum of its ledger, under scripted strategies and under seeded random play.
- These measures limit casual tampering and double charging. They are covered by the project's tests, not by an external review.

## Requests and hosting

- API and WebSocket requests are checked for a same-origin `Origin` header. Request bodies and socket messages are size-limited, and there are in-memory rate limits and connection caps. The one exception to the origin check is the operator surface `/api/mod/*`, which authenticates with a bearer token in a header (see "Moderation" below).
- Rate limits are keyed on the network address. Directly connected, that is the socket's remote address. With `TRUST_PROXY=1` it is the **right-most** `X-Forwarded-For` entry — the address your one trusted proxy saw; anything a client put further left is ignored, so the header cannot be used to dodge a limit. On both hosts an IPv6 address counts as its /64 (one subscriber holds all of it), so changing the last bits of an address is not a new visitor. One address may create 300 new sessions an hour and hold 32 open sockets by default (`NEW_SESSIONS_PER_ADDRESS`, `SOCKETS_PER_ADDRESS`: a campus or a mobile network is one address, so the first is sized for a crowd arriving together and still takes more than a day to fill every place; a visitor past it is told why and when to try again); on the Node host an address many people share without the server being able to tell them apart (loopback or a private range: a proxy without `TRUST_PROXY`, a LAN) is exempt from those two. Set `TRUST_PROXY=1` only when a proxy you control is the only way to reach the server: otherwise a client could write that header itself. Without it, behind a proxy every visitor shares the proxy's address, so add limiting at the proxy.
- The limiter's rows are bounded, and a full limiter makes room by dropping the rows that expire soonest: it never answers a flood of new keys by refusing every newcomer. Rows are kept in three classes (short windows, long windows, and keys that are never dropped: the operator's guard and the account sign-in and reset limits), so keys an outsider can mint and that live long cannot crowd out the keys the game itself depends on.
- The server does not terminate TLS and listens on all interfaces. Put it behind an HTTPS reverse proxy.
- Limits and chat de-duplication live in memory and reset on restart.
- **A route cannot crash the server by answering badly.** Every API answer is turned into text before any header is sent and is written at most once per request. A response that cannot be serialised, an invalid status or header, a module that fails after its answer went out, or anything thrown that is not an error becomes one generic `500 {"error":"internal_error"}` (or nothing more, if an answer was already sent), is logged as one line without request headers, cookies or bodies, and the process keeps running. Route modules may set only `Set-Cookie`, `Cache-Control` and `Retry-After`. A socket error sent to a client carries a machine code only — plus, for a refusal the server explains (a blocked text, a mute), the sentence the server itself wrote (`reason`, repeated as `message`); any other error text stays in the server log.

- **Pages outside `/api/` are written by the host, not by the module that registers them.** The link-preview page `/s/<code>` and the e-mail pages `/e/confirm` and `/e/unsub` are the only HTML the server builds. A module returns `{ status, html }` and nothing else: the host writes every page, at most once per request, with fixed headers a page cannot change — `Content-Security-Policy: default-src 'none'; img-src 'self'; style-src 'unsafe-inline'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'` (no script can run), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, no cookie — under the same per-address limit as the API, and reports them to telemetry by a path template only. A page is handed the path, the query, the public origin and the caller's address — never the request, a header or the session. A page that throws is one generic 500. `POST` is accepted only by a registered page (the one-click unsubscribe), its body is never read, and more than 8 kB of it ends the connection.
- **The origin written into absolute links** (a link preview's `og:url` and `og:image`, also on the game's own page) is `PUBLIC_ORIGIN` when it is a plain `http(s)://host[:port]`; otherwise the request's own `Host` header, used only if it consists of host characters. Nothing else from a request is ever written into a page, and only the two preview-image attributes of the game's page are rewritten.
- **Reaching outside the game is three narrow capabilities.** `ctx.env(name)` answers only for a fixed list of outreach settings and `''` for every other name (the operator token, telemetry keys and the rest of the environment are not reachable through it). `ctx.fetch` refuses anything but `https:`, never follows a redirect, and is cut off after 15 seconds whatever the caller passed; push endpoints must also be a browser vendor's push host. `ctx.keyFile` keeps a secret the server makes for itself in `DATA_DIR/keys/<name>.json` with mode 0600, under a plain name only.
- **Source maps are never served.** They are written only by an opt-in build (`SOURCEMAPS=1`, into `dist-maps/`, outside `dist/`) for upload to Sentry; any path ending in `.map` answers 404.
- **Stopping is ordered.** On `close()`, `SIGINT` and `SIGTERM`: no new outreach round starts and one that is sending is waited for (so what it sent is recorded and never sent again after a restart), then the world registry and the data file are written, then telemetry is flushed. A step that fails is logged and the next still runs; a signal exits after 20 seconds at the latest with what is on disk.

## Home rooms and guests

- A Home room is keyed by its owner's public id. By default only the owner's own sockets can join it.
- **The one exception is an accepted guest.** A visitor knocks (only while the server sees the host connected and at home); the host answers. If let in, the server records the visit — it lasts 30 minutes — and the visitor may then send `join` with `venueId: 'home'` and the host's public id. The room module admits that socket to the host's Home room only if the server's own guest list says the sender is a current, unexpired, unblocked guest of that host in that city **and** the host's stored life is at home. The room key is built from the validated host id, so the message cannot name any other private room; a host id with any other venue, or a malformed one, is refused.
- Membership is re-checked against the stored guest list, not remembered: after the guest's and the host's API requests, and **before any room message of the guest is forwarded** once the entitlement is older than 3 seconds or the visit's own expiry time has passed — so the first chat line, movement or signal at or after the expiry is refused, not delivered. Leaving, being asked to leave or being blocked drops the guest at once; a host whose life leaves home (a trip or the commute) empties the room and the stored visits are closed; a host with no connection in their own Home room for 20 seconds ends the visits too.
- **Guests who send nothing are bounded by time.** On every heartbeat (10 seconds by default) the server re-checks each socket that is visiting a Home room. A visit that has run out, or whose host is no longer at home, ends then — at most one heartbeat after it should — and the stored visit is closed.
- A guest is an ordinary member of the room: they see its presence and chat, and voice follows the existing rules — off and muted on join, proximity-gated signalling, the same cap. Nothing enables voice for anyone. The game client does not offer voice in a house visit.

## Other players and what they can see

- Other players only ever receive your **public id**, your nickname and, for players in the same venue room, your **look** — eight option ids (body, hair, outfit, fabric and four colours) that the server reads from your stored life and re-validates against the option lists when you join. A client cannot supply a look, and the per-move presence message is unchanged.
- Friends see which venue you are in; strangers see only that you are connected. The Neighbours directory and the Rich List show your name, district and balance unless you hide yourself from them.
- Blocking is mutual in effect: it ends a friendship and a visit and stops messages, friend requests, knocks and gifts between the two players. **It also applies in public venues:** the server builds each player's room list for that player and leaves the other out, does not deliver either one's venue chat to the other, and refuses voice signalling between them with the same answer it gives for someone who is not in the room. Everyone else in the venue still sees and hears both, and nothing tells either player that the other is there: one's movement sends the other no frame at all. One shared limit remains — the venue's cap of eight voice participants counts everyone, so a blocked pair can still fill it for each other. Who blocks whom is held in memory for this, loaded when the server starts.
- **Presence has a freshness bound.** Every socket is pinged every 10 seconds (`HEARTBEAT_SECONDS`). A connection that dies without closing stops counting as online once a ping has gone unanswered for 5 seconds — so within 15 seconds it reads "reconnecting" rather than "online", is not listed in a venue, and cannot be knocked on as if at home. It is closed at the next beat (at most 20 seconds) and reads "offline" 20 seconds after that. Friend lists and player cards carry `seenAt`, the server time that connection was last heard from.
- All player text is escaped when shown. Nothing a player types is rendered as markup or as a link, ads are text plus a colour and icon from fixed lists, and there are no uploaded images.
- Elections are open to **sock-puppet voting**: a device session is not a verified person. The friction is deliberate and account-free, and it slows abuse rather than preventing it:
  - one vote per device session, cast in person at the Polling Unit;
  - the voting life must have lived a Lagos day **and been paid for work (a shift or a gig) on at least two different Lagos days** — a puppet has to be played on two separate days, not merely left to age. Running for office needs the same plus the filing fee;
  - a **per-address signal: more than `VOTES_PER_ADDRESS` votes (default 3) from one network address in one election**. The trade-off is plain. One public address is not one person: mobile carriers put thousands of subscribers behind a few addresses (carrier-grade NAT), and a school, an office or a hostel shares one. Refusing the fourth vote from an address would silence real voters far more often than it would stop a cheat, who can switch to mobile data or a VPN anyway. So **by default (`VOTE_CAP_MODE=flag`) every such vote is counted**, and the operator's audit trail gets one line per address per election to look at. An operator who prefers the other error can set `VOTE_CAP_MODE=refuse`: votes past the number from a *public* address are then refused — the voter is told exactly why and that the vote was not counted, and nothing is recorded as cast — while votes from a loopback or private-range address (the server is seeing a proxy without `TRUST_PROXY`, or a LAN) are still counted and logged. In either mode a vote is answered `voted` only when it is on the ballot and in the data file. Addresses are never stored: the ballot keeps a salted hash per address, for the current election only. A hash of an IPv4 address can be reversed by anyone holding the data file and the salt, so treat it as pseudonymous, not anonymous.
- Gifts of in-game naira are limited to money earned from work, per gift, per day and per recipient (₦20,000 received a day). There is no waiting period for a new player or a new friendship, so what bounds money funnelled to one player from many sessions is that each of them has to earn what it gives, and the recipient's daily limit. There is no real money anywhere in the game.

## Moderation

There are no moderator accounts. Whoever holds the server's `MODERATOR_TOKEN` is the operator.

- **Off by default.** Without `MODERATOR_TOKEN` — or with one shorter than 24 characters — every `/api/mod/*` path answers 404, like a route that does not exist.
- **Header-only bearer token.** `Authorization: Bearer <token>` on every request. It is never read from a cookie, a query string or a body, so it does not end up in URLs or access logs of well-behaved proxies. Apart from the environment variable it was started with, the server keeps only a SHA-256 digest of it, compares digests in constant time, never logs it and never writes it to the data file. A device session cookie gives no access.
- **Not tied to an origin, on purpose.** A browser never attaches an `Authorization` header by itself, so these routes cannot be driven by a cross-site request; that is why they work from `curl` without an `Origin`. No CORS headers are sent, so a page on another origin cannot read a response either.
- **Rate limits.** A request **with** the right token is limited to 60 a minute per address and by nothing else: it skips the general per-address limit, so other clients behind the same address (a proxy without `TRUST_PROXY`) cannot use up the operator's budget, and it never touches the failed-attempt counters, so nobody else's failures can lock the operator out. A request **without** the right token passes the general per-address limit and is then counted: 10 per address and 100 from all addresses together per 10 minutes, after which it gets 429 until the window passes. Be clear about what this is: anyone holding the token is the operator, with no second factor and no lockout, and the counters only slow guessing down. The protection is the token's length — use a long random one and send it only over HTTPS.
- The token must be 24 to 512 printable ASCII characters without spaces (what a Bearer header can carry); anything else leaves the feature off, with a warning at start-up that does not print it.
- **What an operator can read:** player reports (reason, the reporter's text, up to five of the reported player's direct messages to the reporter), problem reports with their automatic context, active mutes, live ads, announcements and shout-outs, and the audit trail. Nothing returned contains a session secret. Direct messages other than that evidence are not exposed by any route.
- **What an operator can do:** dismiss a report; set a problem report's status and note; mute a public id from posting text for 1 minute to 30 days; lift a mute; remove an ad, an announcement or a shout-out. Each writes an audit line with the time, the target and the address it came from; the last 1,000 are kept.
- **A mute is not a ban and deletes nothing.** It stops venue chat, messages, group names, slogans, announcements, ads, shout-outs and renaming until it ends. A muted player who sends their current name again keeps their session (it is renewed), but the name is not written or announced to the room again. The player keeps their session, life, money and belongings, can still play, read, vote and receive messages, is told the reason and the end time, and can still file a problem report. No operator action archives, edits or deletes a life.
- **Text filter.** Every text another player can read is checked on the server: nicknames (on creation and rename), venue chat, direct, group and house messages, group names, slogans, announcements, ad text, song titles and artists. The list (`server/moderation/terms.ts`) is short and conservative — slurs, telling someone to harm themselves, sexual content about children — and is matched on whole words after folding case, accents, look-alike digits, spaced-out letters and stretched letters. Nicknames, group names and every civic line also refuse links, phone numbers, e-mail addresses and handles on other apps. A refused text is **rejected with a reason and never altered**: nothing is starred out or delivered in part. It is a seatbelt, not a moderator — easy to evade deliberately, blind to context and to most languages.
- **Problem reports.** Any player can file one from inside the game; no outside account exists or is needed. The stored report holds the public id, name, category, text and context built field by field from the server's copy of the life (build, city, cash, location, running action, last message, last ten actions with result codes, last ten wallet lines). It cannot contain the session secret, and a test checks that it does not. Three filings an hour per player, ten per address, five open at a time.
- **Limits of all this.** One shared secret means no per-moderator accountability: the audit trail records an address, not a person. There is no ban for a player who makes new sessions, and a muted player can create a new session and keep talking until that one is muted too. Venue chat is not stored, so reports about it arrive without evidence.

## Stored data

- Sessions, nicknames, game state and archived lives are written to one unencrypted JSON file, `devices.json`, in the data directory (file mode `0600`). It contains the session secrets. Protect and back up that directory yourself, and never commit it.
- The same file holds four more collections. `social`: friends, blocks, conversations and their messages (direct, group and house chats, a bounded history each), house visits, pending gifts and reports. (Receipts of gifts, interactions, groups and paid civic requests are kept in each player's session record, beside their action receipts.) `civic`: list preferences and, per city, the residents directory with each resident's last balance, elections and announcements (with a salted hash per voting address for the current election), ads, hunt counters and radio queues. `moderation`: mutes and the audit trail, including the address each operator request came from. `support`: problem reports with their context. All four identify players by public id only; the session secret is never written to them.
- **The world registry** is beside the data file, in `DATA_DIR/world/`: one append-only file per local government holding, per resident, the public id, the name shown in the directory, the plot and the packed look of the house. A player hidden from the directory keeps their house on the map without their name or id. A resident not seen for 45 days leaves it with their plot.
- **About one player the server holds:** the nickname and the lives (in `sessions`, under the cookie secret); the local government id they chose and their plot; and, in `growth` under the public id, their share links and referral record, salted hashes of up to four device tokens, the age answer (`adult` / `minor`), an optional e-mail address (only after the consent box, see "Messages outside the game"), push subscriptions, table ratings and — for 31 days — a first-day / last-day / funnel-step record for the operator's cohort table. It holds no position, no IP address, no voice audio and no venue chat.
- Every collection is capped; the caps are listed in the README under "Storage and limits". Archived lives of players who actually played are the one thing never deleted automatically.
- **Direct, group and house messages are stored in plain text** and can be read by whoever can read the data file. Venue chat is relayed to the room and not written to disk.
- The browser caches the last known game state and nickname in `localStorage` for display, and keeps the sound preferences and which notices you have read there too. During the first minute it also keeps the draft name and character of the landing screen, the id of the one "Play" request (so a retry or a reload is the same request to the server), the public id an invite link pointed at, the share code and table id that link carried, a random device token (sent with a referral link and stored by the server only as a salted hash), and how often settling in was offered. None of these is a credential. When telemetry is configured it also keeps the player's analytics choice there (and, after Accept only, which funnel steps were already reported and PostHog's own state).

## Chat, presence and location

- Joining a venue room shows your nickname, public ID and voice status to everyone in that room.
- Chat is plain text relayed through the server. It is not end-to-end encrypted. Venue chat passes the text filter and the sender's mute state, and is not delivered between two players of whom either has blocked the other; see "Other players" and "Moderation" above.
- The optional "use my location" control asks the browser for your position and uses it in the browser to suggest a city. The position is not sent to the server.

## The Worker host

The Cloudflare Worker (`deploy/`) runs the same route and socket modules over the same context, so every property in this document holds there too. What is specific to it:

- **Storage.** Everything is in the SQLite storage of one Durable Object: sessions (with their secrets, as on Node), action receipts and exactly-once receipts in tables of their own, archived lives, the feature collections, the world's shards as rows, the keys the server makes for itself (`host_keys`: the push keys and the link-signing key — never in a collection, a response or a log), durable rate-limit windows, the relay test's daily budget, and venue-chat retry receipts (an id, a time and a digest of the body; never the text). Protect access to the Cloudflare account as you would the data directory.
- **A failed write has no effect there either.** A write is one SQLite transaction — the session, its receipts, the archives and the collections together — followed by a durability barrier before it is acknowledged. A commit that fails is answered `503 storage_unavailable` with the store's own sentence and never with the SQL error. If the barrier itself fails the outcome is unknown: the store refuses everything until the object restarts, and a retry then meets the receipt if the commit was kept.
- **Addresses.** The Worker never stores or keys on a raw address: limits and caps use a SHA-256 digest of `CF-Connecting-IP` (for IPv6, of its /64). `TRUST_PROXY` does not exist there.
- **The operator surface** is off unless the `MODERATOR_TOKEN` secret is set (24–512 printable characters). Only a digest of it is kept in memory; a bearer token is compared by digest without stopping at the first difference; a cookie or a query value is never accepted. The Worker's own origin check exempts `/api/mod/*` exactly as the Node host does.
- **Sockets sleep.** A hibernating socket's attachment holds its public identity, its cookie secret (host-private: it is how the session is found again), room, position, voice state and look. Nothing in an attachment is ever sent to another player. After a sleep every socket's room is re-checked against the stored life before its next room message is forwarded.
- **Outside requests** are `https` only, never follow a redirect (the answer to one is rejected) and are cut off after 15 seconds.
- **The original Allworld character.** `/old-character.html` exists only on the apex host (`https://joinallworld.com`), answers only `GET` and `HEAD`, is never cached, and sends no referrer. It moves a legacy guest identity to the original game through the old site's own scope; it reads and writes nothing of this game's sessions. The link to it in the landing, the session sheet and the menu is ordinary navigation.

## The University of Lagos campus

The campus is a fictional game layer. Nothing in it is a real admission, fee, room allocation, result or job, and it is not affiliated with the university. Its shared state is one weekly election (at most 16 candidates and 2,048 ballots, public ids and student ids the game made). A ballot or a nomination takes the player's identity, faculty and hall from their stored life — never from the request — and is saved in the same transaction as its exactly-once receipt; the public action route cannot run either. A guest of the quick start can visit but cannot become a student. Campus positions are checked against the campus's walkable ground on the server.

## Voice

**Voice has not yet been verified with real audio between two clients.** Treat it as experimental.

- **Opt-in.** The microphone is not requested until you press Join voice. The browser asks for permission and requires HTTPS or `localhost`. You join muted and unmute yourself. Leaving voice, changing room or closing the page stops the microphone.
- **Peer-to-peer.** Audio goes directly between browsers (or through the configured relay in the bounded test below), not through the game server, which only relays connection setup messages between people in the same room. As a consequence, **people you connect to can learn your IP address**, and with it your approximate location and network provider. Do not enable voice if that is unacceptable.
- **Third-party STUN.** To find a route between browsers, the client contacts a public STUN server operated by Google (`stun.l.google.com`). That server sees your IP address, not your audio. Self-hosters can change it in `src/community.ts`.
- **Relay is restricted.** The Node server issues no relay credentials. On the Worker host the optional Cloudflare TURN adapter can issue short-lived credentials only to at most two explicitly allowed test devices, with a bounded number of mint attempts a day; general relay issuance is disabled. When a relay is selected, audio passes through that provider. These application limits are not a provider spending cap, and provider secrets are never placed in frontend code. Everywhere else, on some mobile, corporate or carrier-grade NAT networks, calls will not connect.
- **No recording by the project.** The server never receives audio and the project's code does not record it. Nothing stops another participant from recording on their own device.

## Growth features: what is stored and what pays

Everything below lives in one collection, `growth`, under public ids only. Shapes and caps: `server/growth/data.ts`, `outreach.js`, `metrics.js`, `tables.js`.

- **What pays, and only once.** Missions are ordinary game actions (exactly once by action id). A table win and the two referral gifts are server-only actions (`growth.table-result`, `growth.referral`): a player cannot send them, and the route runs them in the same transaction that removes the pending result or sets the referral flag, so a replay finds nothing to pay. The life itself holds the caps: four paid table wins a day, one welcome gift per life, five referral rewards a week and twenty for life. `npm run economy` plays a strategy that reaches every cap and asserts the budget.
- **Referral cannot be farmed for more than its price.** Both gifts wait for paid work on real Lagos days (one for the newcomer's gift, two for the inviter's). A link attaches only to a life at most three days old, once, never to your own link or to someone you invited. A device token (random, kept in the browser, stored only as a salted hash) refuses a second life on the same phone; more than three links to one inviter from one network address in seven days are refused (the address is compared in memory and never stored). Neither stops someone who clears their browser and changes network: what bounds that is two real days of shifts per ₦1,500, twenty times, and that reward money cannot be gifted on.
- **Share links.** A code maps to facts the server read from the sharer's own life; the only player text is the display name, already filtered. The preview page `/s/<code>` is static HTML with every value escaped, no script, no cookie, and a content-security policy that allows none. Twenty new links a day per player, 20,000 on the server, 30 days.
- **Tables.** The server deals from a seed it never sends, holds every hand, and sends each socket only that seat's view; a watcher's view has no hand. A move carries its number and is applied once. No stakes exist. Collusion is bounded by the per-pair cap (three counted games a day) and the daily paid cap, both below the gift limits. Live matches are in memory only.
- **Metrics.** Daily totals and retention cohorts, counted from requests the server already handles. A life is followed individually (first day, last day seen, funnel steps) for 31 days, then that record is deleted; totals are kept 400 days and cohorts 120. The operator's report holds no player id, name, address or text. These first-party numbers need no consent sheet because they hold no person; they are counted whether or not telemetry is configured, are never forwarded to an analytics service and never mixed with its events (the operator's report says `source: 'first-party'` and whether analytics also runs). Each thing is counted once under one name. Product events are emitted in the browser as `jaw:track` DOM events with no names, text, addresses or positions in them; they go to PostHog only when telemetry is configured **and** the player accepted (see "Telemetry").

## Messages outside the game

The game reaches a player outside the game only by web push and e-mail, only if they asked, and never if they said they are under 18. The module that sends is `server/growth/outreach.ts`.

- **Age first.** `POST /api/growth/consent` records "18 or older" or "under 18". An answer of under 18 is not raised by asking again on the same life, deletes anything stored for a channel, and makes every channel refuse.
- **E-mail consent, word for word:** "Send me Allworld e-mails at this address: one to confirm it now, then at most one message a day and three a week about my character, my friends and events, and a weekly summary. A friend can also ping me to join them: at most two such e-mails a day. I can stop with one tap in any e-mail or here. I am 18 or older." The address is stored only after this box is ticked (it is not pre-ticked), and only one message — the confirmation — is sent until the player opens its link **and presses the button on that page** (a GET confirms nothing, so a mail scanner cannot opt anyone in). The link is signed (HMAC-SHA-256, key in `DATA_DIR/keys/growth-signing.json`, mode 0600), names the contact's current nonce and expires after 48 hours; changing the address invalidates it. Three confirmations a day per player, and three a day to one address whoever asks (counted under a salted hash of it); confirmations stop when the server's daily total is used up and may use at most half of it.
- **Push consent, word for word:** "Send notifications to this phone: at most one a day and three a week, never at night, about my character, my friends and events. I can switch them off here at any time." Shown by the game before the browser's own prompt, never on arrival. A subscription's endpoint must be a browser vendor's push service (`PUSH_HOSTS` in `webpush.js`), so the server cannot be made to POST to an arbitrary address.
- **Where the address is.** In `growth.contacts[publicId]` and nowhere else: not in a life, a profile, a share, a metric, the outreach log or a server log line. Its owner is shown it masked (`a•••@e•••.com`); no other player and no route returns it. A dry-run preview is stored without the address and with link signatures cut off.
- **Stopping.** The unsubscribe link in every message, a mail program's one-click unsubscribe (RFC 8058: `List-Unsubscribe` with an HTTPS address and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, answered by an unauthenticated POST keyed by a signed token), and "Delete my address" in the game each delete the address at once. Switching notifications off, or a push service answering 404 or 410, deletes the subscription.
- **Frequency.** Push: one message a day, three a week, none between 22:00 and 07:00 Lagos time, 1 then 3 then 7 days apart when messages bring no visit, none after four until the player returns by themselves. E-mail (comeback mail and the weekly digest share one ledger): one a day and three a week across every type, none between 21:00 and 08:00 Lagos time, none within 12 hours of a visit, one every 14 days after three with no visit in between, and nothing after the 28-day goodbye or five mails in a row with no visit, until the player returns. A scheduled message's period is claimed in a saved transaction before it is attempted, so a crash or a provider failure can only skip it, never send it twice. `EMAIL_DAILY_CAP` and `PUSH_DAILY_CAP` bound the server's total.
- **Comeback mail.** A confirmed address is also written to about the player's character (a need that has fallen low, friends waiting or asking for them back, a milestone, an event the next day, 3, 7 and 28 days away), only while "E-mail me about my character" is on, which starts on when an address is confirmed (an address confirmed earlier starts off) and has a switch per type and a 30-day pause in Stay in touch. Every mail carries a one-click link to stop its type, one to unsubscribe from everything, and the `List-Unsubscribe` headers; none needs a login. Mails name friends only, never carry message text, balances, positions or another player's address, and never go for a blocked or muted sender. The nudge (`POST /api/growth/nudge`) answers the same whether or not the friend has an address. The recipient is chosen by `mailRecipientOf` in `server/growth/recipient.ts`. Rules and numbers: `docs/COMEBACK-MAIL.md`.
- **The provider.** Zoho ZeptoMail, through `https://api.zeptomail.com/v1.1/sg/email`. The key is read from `ZEPTOMAIL_AUTH`, sent only as that request's `Authorization` header, and never logged, stored or returned; a failure is recorded as a status code. 4xx is not retried; 429, 5xx and timeouts are retried at most three times. With the key, the sender address or `PUBLIC_ORIGIN` unset, e-mail is in **dry-run**: composed, kept as a preview, logged as `dry-run`, not sent.
- **The operator** sees, behind the operator token (`GET /api/mod/growth/outreach`): whether each channel is live or dry-run, opt-ins, what was sent today against the cap, the last error, the last 100 log lines and the last dry-run previews — without any address, endpoint or player id — and can switch a channel off (`POST …/switch`).
- **Retention.** A contact or subscription is kept until its owner removes it, or until the player has not been seen for 60 days, when their growth record is forgotten with it.

**What the operator must do outside the code before e-mail is switched on**

1. In ZeptoMail, add and verify the sending domain, and create a mail agent; put its send token in `ZEPTOMAIL_AUTH` on the server (never in the repository).
2. Publish the DNS records ZeptoMail gives for that domain: SPF and DKIM, and a DMARC record (start with `p=none` and a reporting address). Gmail and Yahoo require all three for bulk senders, and a spam-complaint rate under 0.3%.
3. Set `EMAIL_FROM_ADDRESS` (on that domain), `PUBLIC_ORIGIN` (the game's HTTPS address) and `EMAIL_CONTACT_LINE` (a postal or contact line; US law requires a postal address in commercial e-mail).
4. ZeptoMail is a service for transactional and triggered mail, not bulk marketing. This digest is opt-in, confirmed and triggered by the recipient's own absence or week; keep it that way, and read their usage policy before adding any broadcast.
5. Nigeria's data-protection directive (GAID 2025) requires consent for direct marketing and registration of controllers "of major importance" with the Nigeria Data Protection Commission; a game with more than a few hundred players is likely to qualify. Confirm the registration tier and the age of consent with a Nigerian lawyer before going live. Until then the game treats under-18 as "no outside messages".
6. Send the first real message to yourself and check the headers (`List-Unsubscribe`, DKIM pass) before letting the schedule run: this build has only been tested against a fake provider. It has not been verified that ZeptoMail's SendGrid-compatible endpoint passes custom `headers` through; if it does not, the one-click header is missing and the visible link still works.

## Telemetry

**Off unless an operator configures it.** With no telemetry variable set (README, "Telemetry") nothing below happens: no request to either service, no SDK code run or downloaded, nothing stored. It also never runs on `localhost` or a private address unless `TELEMETRY_DEBUG=1`. When it is configured there are two separate things, with different rules.

### Error reports (Sentry) — always on, no personal data

Sent without asking, as a diagnostic the game needs to be kept working. A report contains: the error type and message, stack frames (file, function, line — no local variables), the release (`BUILD_ID`) and environment, the browser's user-agent string, the page's origin and path, up to 30 breadcrumbs that are **action types, result codes, screen names and connection states only**, and the session's **public id** (the code other players already see). The server's reports carry a route **template** (`POST /api/social/house/:host`), an action type and a result code.

- It never contains chat or message text, a nickname, an email address, a position, a query string, a request body, a header or a cookie. This is enforced by an allow-list, not a filter: every report is rebuilt from named fields (`src/telemetry/scrub.ts`), every string in it is rewritten (emails, UUIDs, tokens, coordinates, long numbers, query strings and quoted prose are replaced), and whatever the player is known to have typed — the failing request's own strings, the text fields on the page, the nickname — is removed from the message first.
- The user id is the public id and nothing else. The session cookie is `HttpOnly`, so browser code cannot read it; on the server it never enters a report, and any UUID found in report text is replaced.
- No cookies and no browser storage are used. None of the SDK's automatic breadcrumbs (console, clicks, network, navigation) are installed, and there is no browser performance tracing.
- **IP addresses.** The SDK is told not to let Sentry infer one (`dataCollection.userInfo: false`; since SDK 11 `sendDefaultPii: false` alone does not do this). Sentry still sees the connection's address when a report arrives, so the operator **must also** switch on, in each Sentry project: *Settings → Security & Privacy → **Prevent Storing of IP Addresses***, and leave *Data Scrubber* and *Use Default Scrubbers* on.
- **Session replay is off.** It exists only behind `TELEMETRY_REPLAY_ON_ERROR=1`; then it records only sessions that hit an error, with all text and inputs masked, media blocked and no canvas recorded. Turning it on changes what is collected: update the player-facing text first.
- The same failure is reported at most five times a minute per server process.

### Usage analytics (PostHog) — only after the player accepts

- **Consent first.** A sheet in the game asks once — after a new player's first reward by default (a returning player: a few seconds into the visit), never during the first-minute flow and never on top of another sheet: if the game opens a sheet while the question is unanswered, the question closes with no answer recorded and is asked again after that sheet has closed — with **Accept** and **Reject** as two identical buttons and the full "What we collect" text one tap away. Until the player answers, nothing is sent and the PostHog code is not downloaded; events that happen meanwhile wait in memory only, are sent if the answer is Accept and are discarded if it is Reject. After Reject nothing is sent, ever, and the only thing kept on the device is the choice itself. The choice can be changed in Settings → Privacy → *Analytics and error reports*; Reject after Accept stops the SDK and clears what it had stored.
- **Do Not Track and Global Privacy Control are a Reject**, whatever was chosen before, and the sheet is not shown. **A player who said they are under 18 has analytics off.** The age answer has one home — the growth collection, set by `POST /api/growth/consent`, the same answer e-mail and push are refused on — and it reaches analytics three ways: the server forgets any Accept it held for that player the moment the answer is saved and refuses a later one (`POST /api/telemetry/consent` → `{ analytics: false, under18: true }`); `GET /api/telemetry/config` adds `under18: true` for that player's session, so their browser never loads the analytics SDK; and the page announces the answer when it is given (`jaw:age`), which stops an SDK that was already running. An answer of under 18 is not raised by asking again on the same life.
- **What is sent** is the event catalogue in `src/telemetry/events.ts` and nothing else: funnel steps of the first minute and of settling in, what is used (missions collected, table games sat down to and how they end, links shared or arrived by, channels switched on or off), counts of interactions (never their content), coarse performance and connection health. A test reads the game's sources and fails if a reported event is missing from the catalogue or carries a property it would drop. The name a player types is never sent — only whether the suggested one was edited and how long it is. Properties are numbers, booleans and short id-like words, checked against the catalogue by name and type; a nickname, free text, an email, a position, an IP address or any UUID is refused. The distinct id is the session's **public id**. Page URLs are reduced to origin and path. GeoIP lookup is disabled on every event (`$geoip_disable`), so no location is derived from the address; the local government a player chose for their house (an id from a fixed list of twenty, chosen by them — never a position) is attached as a coarse group once it is confirmed.
- **What is switched off in the SDK:** autocapture of clicks and inputs, rage/dead clicks, heatmaps, session recording, surveys, feature flags, web vitals and exception capture. The build used cannot download further scripts from PostHog. Storage is `localStorage` under one name — no cookies, nothing shared across subdomains — and person profiles are created for identified players only.
- **The server's events follow the same choice.** The browser tells the server Accept or Reject (`POST /api/telemetry/consent`); the server keeps that in memory only, records nothing for a player without an Accept on record, and is told again on each page load.
- **IP addresses.** PostHog sees the connection's address when an event arrives. The operator **must** switch on *Project settings → General → **Discard client IP data***.
- **Where it goes.** PostHog and Sentry process the data on the operator's behalf, in the region of the configured host (`POSTHOG_HOST`, the Sentry DSN). The default PostHog host is the US cloud; for players in Nigeria, the EU or the UK that is a transfer abroad which the operator's privacy notice must cover, or the EU host can be configured instead.

### What the operator must do

1. In Sentry (both projects): *Prevent Storing of IP Addresses* on; data scrubbers on.
2. In PostHog: *Discard client IP data* on; session recording and autocapture left off in the project as well.
3. Keep the player-facing text (`src/telemetry/what-we-collect.ts`) and this section true whenever an event or a flag is added.
4. Never put a secret in a telemetry variable: the client DSN and the `phc_` key are public by design and are the only two values sent to the browser. The source-map token (`SENTRY_AUTH_TOKEN`) is used at build time only and is not read by the server.

Source maps are uploaded to Sentry and are never served by the game (`*.map` answers 404).

## Out of scope

- Denial of service against a self-hosted instance with no proxy-level limits.
- Impersonation by nickname, which is a documented limitation above.
- Issues that require access to the server's data directory or the user's own browser profile.
