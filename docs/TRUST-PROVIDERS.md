# Phase R trust providers

Research and local implementation checked 7 October 2026. Firebase phone and Dojah ID are the selected providers. This is not live activation or legal advice.

## Existing boundary

The original generic provider registry remains empty. The explicit Firebase and Dojah integrations are now in `server/trust/phone.ts` and `server/trust/dojah.ts`; without reviewed configuration their routes return `provider_unavailable`; `server/trust/service.ts` records only tier, `by`, time, and optional reference. Admins can grant a checked tier by hand through the existing audited admin action. Keep that path available while providers are absent or pending. A provider outage, pending result, unsupported flow, or unconfigured secret must never grant a provider tier.

The Firebase verifier in `server/accounts/token.ts` currently accepts only Google and email/password sign-in tokens. It checks signature, project `aud`, `https://securetoken.google.com/<projectId>` issuer, freshness, subject, and verified email; it rejects `firebase.sign_in_provider=phone`. That is the current account sign-in policy and should remain so: phone verification must not silently become phone-only Allworld sign-in.

## T1 phone check: link Firebase phone to the existing account

Use Firebase Auth's client phone-link flow on the already authenticated Firebase user: `linkWithPhoneNumber(user, phoneNumber, appVerifier)`, then confirm the returned OTP. Firebase documents linking to the existing user. Use the refreshed ID token only to prove the link. Do not send the phone number or OTP to Allworld. Google's phone-auth docs say Google receives and stores the number for abuse prevention; disclose this processing and obtain consent before invoking the flow.

The Firebase Admin `DecodedIdToken` reference documents a signed `phone_number` claim “if available,” and the `firebase` claim records sign-in provider and identity details. A minimal verifier extension can derive a boolean phone-linked fact from a valid token carrying the Firebase-issued phone claim, while still requiring an existing email/password or Google sign-in provider and verified email. Do not return or persist the claim value. Confirm in a Firebase sandbox that a phone-linked, email/password- or Google-authenticated account's refreshed token contains this claim; if not, use a server-side Firebase Admin lookup of linked provider data by the verified UID, with the required service account, and return only a boolean. Never accept a browser-supplied provider list or phone number as proof. Firebase token identity claims are provider-authenticated, but current Allworld token parsing does not yet expose this fact.

**Operator setup:** enable Phone as a Firebase Authentication provider; set allowed SMS regions (Firebase says new projects default to no regions); authorize the production domain. Keep Google/email sign-in enabled. No Allworld SMS vendor credential is needed. Firebase's documented link API accepts E.164 input and an application verifier; handle “already linked” and “credential already in use” as non-success without trying to merge accounts implicitly.

**Storage:** retain only `tier: 'phone'`, `by: 'provider'`, timestamp, and a random opaque check reference. Do not store/log the phone number, OTP, token claim, raw token, or provider identity data. The Firebase account itself remains the phone system of record.

## ID / age check: Dojah EasyOnboard as the first hosted-flow candidate

Dojah documents an EasyOnboard hosted verification flow, a web `Connect` widget, a server subscription to `kyc_widget`, and signed webhook results. Launch with `app_id`, client-safe `p_key`, configured `widget_id`, and a server-generated random `reference_id` (at least 10 characters); omit `user_data`, `gov_data`, and custom metadata unless a separately reviewed need exists. Do not use the client `onSuccess` to grant a tier. Confirm the webhook's `reference_id` maps to a pending check for the same Allworld player and configured widget, then make one idempotent state transition. The `widget_id` in the sample event and the per-subscription signature provide provider/configuration binding; reject unknown references/widgets/environments.

Register the callback using `POST https://api.dojah.io/api/v1/webhook/subscribe` with raw `Authorization: <secret_key>` (no `Bearer`), `AppId: <app_id>`, and JSON `{ "webhook": "https://<host>/...", "service": "kyc_widget" }`. Keep `DOJAH_APP_ID` and `DOJAH_SECRET_KEY` server-side. The widget uses public `app_id`/`p_key`; `DOJAH_WIDGET_ID` is the published flow id. Copy the subscription's distinct signing secret into `DOJAH_WEBHOOK_SECRET`.

Verify `x-dojah-signature` as lowercase hex HMAC-SHA256 over the exact raw request bytes, keyed by `DOJAH_WEBHOOK_SECRET`, with constant-time comparison, before parsing or acting. Dojah also documents `x-dojah-signature-v2` as SHA-256 of the secret alone; prefer the payload-bound HMAC. The API secret is not the webhook secret. Dojah documents a fixed source IP allowlist option (`135.119.89.106`) as an additional control. Docs do **not** specify a signed timestamp or event ID/replay window. Therefore implement local idempotency: generate an unguessable one-use reference, bind it to the pending account/player and widget, atomically accept only the first eligible terminal result, and make duplicate deliveries a no-op. Do not invent a vendor replay guarantee.

Dojah says webhook `verification_status` is authoritative; its separate lifecycle statuses include Ongoing, Pending, Completed, Failed, and Abandoned. Grant ID tier only when a verified webhook is completed **and** the specific configured ID check passes. ID and birth-date values, document/selfie URLs, and nested result data can be present in webhook payloads. Parse only the required pass/age outcome in memory; never log or persist the raw body, ID/NIN/BVN, DOB, names, images, URLs, or full response. Its docs say file links expire and recommend copying them; explicitly do not follow that recommendation for Allworld.

**Provider questions before enabling:** ask Dojah to confirm a published Nigeria-capable flow that verifies an eligible government ID and an 18+ threshold without requiring BVN/NIN lookup; identify the exact machine-readable step/status fields and final pass semantics (the docs establish generic status, not the exact age-rule contract). Confirm whether the flow can avoid collecting unnecessary identifiers and what vendor-side retention, access, deletion, and subprocessor controls apply. Do not mark `id` or adult until the chosen flow and exact result mapping are confirmed in sandbox and provider terms/configuration reviewed by the operator.

**Operator setup:** Dojah account and production/compliance activation, app, public key, secret key, published EasyOnboard widget/flow id, configured country/document and age rule, HTTPS callback URL, `kyc_widget` webhook subscription, and its separate webhook secret. Production/live keys and billing are separate from sandbox. Until those facts and live proof exist, keep the provider unavailable; existing admin review remains the only way to award tiers.

Smile ID is not selected for this first integration: its current official docs were not retrievable in this research pass for a complete hosted-flow contract. Its older official documentation/search material describes partner ID/signatures and callbacks but is insufficient to certify current hosted integration, webhook replay handling, and the requested minimal-result flow. Re-evaluate only from current first-party hosted-web docs and a confirmed account configuration; do not infer those details from SDKs or marketing pages.

## Live proof gates

Before enabling either provider, prove on sandbox that (1) the existing account stays the same after phone linking and the refreshed verified token exposes a server-verifiable linked-phone fact, while a phone-only sign-in remains refused; (2) an ID flow produces the configured pass, fail, pending, abandoned, and replay cases; (3) bad signatures, wrong widget/environment, unknown references, duplicate callbacks, and mismatched players cannot change tiers; and (4) durable records and logs contain only outcome, tier, timestamp, and opaque reference. Then separately verify provider production activation/configuration. Sandbox completion is not production proof.

## Local implementation checkpoint

Phone and ID panels load only from trust settings. Phone linking sends the number and SMS code directly to Google's Identity Toolkit REST API. The account store retains the proof in memory, cancels it when the panel closes, and refreshes the original Google/password token after linking. The server checks a signed linked-phone fact against the same claimed account, strict origin, CSRF and a retry receipt. Phone-only sign-in remains refused. Confirm that the original refresh token retains its Google/password provider and receives the phone claim in the real sandbox before enabling the flag.

Dojah callbacks use bounded raw request bytes on both hosts, rather than reserialized JSON. The current mapping requires `verification_status: Completed`, top-level success, successful `data.id` and `data.selfie`, and an 18+ birthday derived temporarily from `data.id.data.id_data.date_of_birth`. A published flow must prove that these fields mean authenticated ID and matching live selfie, not simple collection. This mapping is based on the provider's documented widget sample and remains behind `DOJAH_FLOW_REVIEWED=1`. No DOB, number, image or raw callback is saved. Sandbox results never grant a real-player badge. References expire after two hours and the first terminal result wins. Account deletion removes active and parked-character check records.

Security headers add only the required reCAPTCHA and Dojah origins when their configuration is enabled. Camera permission is delegated only to the configured Dojah frame origins, not to the game itself. The widget's browser success callback only triggers a server-status read; it never grants a badge.

Local evidence is `evidence/neighbourhood/provider-http.json`, produced by `/tmp/allworld-provider-http.mjs`. It uses synthetic RSA/HMAC keys and an isolated Node server. It verifies same-account phone proof, retry, wrong-account denial, bad callback signature/widget refusal, pending versus terminal results, data minimization and deletion. Existing token checks passed 12/12; existing trust/security checks passed 27/27. The latter logged a fixture shutdown write warning despite passing. Client transport/CSP diagnostics passed. These do not prove live SMS, a real Dojah flow, or Worker callback runtime.

Operator configuration is documented in `.env.example`. No real environment values, provider jobs or SMS sends were changed or created during implementation.
