# Household authority and lifecycle gap map

Read-only inspection of `worker-household-identity` at `e52cae83fcbc31348f8b7160790ff37c9c22855c` (parent `d3a2138507215906eb53c75304ef00b3d102d5ba`). The working tree was clean. No production source was changed for this report.

## Findings

### Trusted session and life identity

There is a trusted session boundary, but no canonical active LifeId assignment or locator writer. `sessionOfCookie` in `server/protocol.ts` (SHA-256 `27742061f222dc021d6882a9f2a2372a3eb30c3b40ebdde7b5b909462a59dbf5`) resolves a stored session from the cookie and account binding. `server/server.ts` (SHA-256 `c551d2a3f1b157b908cbc7ab6dc57d993019d43cf73494bb0f5cf9e49722d5e7`) creates the request session from that trusted host context; request-body identity is not needed. `SessionRecord.publicId` is the externally visible character key, and `SessionRecord.rev` orders character settlements, but neither is a LifeId nor a per-life/location revision (`server/types.ts`, SHA-256 `4c21ae4c7b1166c9cd83bd8052a8e63ca6b634335168954b5a3b237c51c91b07`).

`settleCity` in `server/life-service.ts` (SHA-256 `f4801b7f35a48a3abebc10837a95f65620bbbfd499478664fffc8d06c7cb3818`) creates missing `CityLifeRecord`s and increments `session.rev`; it does not assign `identity`. `lifeAuthority().settle` in `server/host-context.ts` (SHA-256 `a17e6d27d37c0e60a91ffb739476a360164439d2ac39d5f17c2479f8785a4ab4`) is the shared trusted settlement seam and currently calls `settleCity` only. The optional identity type is present, and `planLifeIdentityAssignment` / `planLifeIdentityMove` in `server/households/lifeIdentity.ts` are pure planning functions, but repository search found no production callers that persist their plans. `characterCity`, `normalizeCharacter`, `fileCharacter`, and `swapLegacyLife` in `server/character.ts` move/choose city slots and legacy lives without a locator/revision hook. `migrateCharacters` and `rekey` in `server/world/service.ts` likewise maintain character filing, not household identity.

The main lifecycle seams that would need an allocated writer are `settleCity`/`lifeAuthority().settle` for first-life creation and active identity, plus `fileCharacter`/`swapLegacyLife` and `server/world/service.ts` `rekey` for movement and city-slot transitions. The host compositions are `server/server.ts` and `deploy/cloudflare-worker.ts` (SHA-256 `b53d611a9d3cf71c400a186eef8aa8c0495dce7df14c6623ada4ca42d68a6982`) and must provide any trusted identifier-generation dependency consistently. Do not substitute the public `publicId`, city key, estate address, or `session.rev` for LifeId or its revisions without a separately reviewed identity model.

### Archive, account park/restore, and receipts

`sessionArchiver` in `server/host-context.ts` calls `archivedLife` in `server/protocol.ts` and deletes the active session. `archivedLife` copies city and legacy-life records; if identity were already stored on each record it would travel with the record, but no household locator/index is updated today. Account lifecycle has additional concrete seams in `server/accounts/service.ts` (SHA-256 `2ed2d63e5bce80c681defd1c29acd2e1d6ec2d2568506eef7ffd82eba2275b1f`): `fromArchive`, `activeCharacter`, `adopt`, `park`, `switchCharacter`, and `deleteAccount` move, restore, or erase character records. They preserve the existing publicId across park/restore; none updates household life/home/member/invite ownership or locators.

Existing `ctx.once` receipts are scoped to the character publicId. Node may inline them on session/archive records; the Worker stores them in its separate `once_receipts` table. `sessionArchiver` intentionally drops expired retry-window receipts, while account park/restore preserves available receipts. The household service binds its command to the current trusted life fact and receipt in one transaction, but no production route invokes it. Do not add an archive fallback that changes receipt semantics; allocate lifecycle hooks around the existing owner transaction if later requirements demand receipt ownership transitions.

`createOnce` in `server/routes/once.ts` (SHA-256 `6072fa044253a38d35b948a33163ea0a2e787ef197bcce3d3760393be94b7046`) registers allowed kinds and maintains a global count. The Node path recounts across session receipt maps (`db.$store.scanSessions` or `Object.values(db.sessions)`); the Worker path uses SQL aggregate counts. This inherited cost is a global receipt-count scan on Node, not a household point-read cost. Preserve the existing scan/cap behavior; do not claim the transaction is globally row-bounded merely because household reads are point reads.

### Home authority

No durable canonical home entity, owner LifeId binding, incarnation, epoch, or lifecycle revision currently exists. `EstateState` in `src/types/life.ts` (SHA-256 `a57338328b05b9277ac4b5497acd2d54ae17f3bb303f30f25d1eb19ac9a98a73`) is embedded in a life: it carries the selected city/LGA, plot address, current/away residence, main-home city, and confirmation. It has no stable HomeId or lifecycle epoch. `mainHomeUnit` / `mainHomeKey` in `src/game/residence.ts` (SHA-256 `b7353aa3466b3b1287568744227ad3a87c6e74e8b653030ca2ea03948a441c87`) derive a display/location key from that mutable state; they are not ownership authority.

The game rules in `src/game/systems/estate.ts` (SHA-256 `e4bfc0fd555c67b7389bef0901ead7a8eb81cfde9bff9ba54e79650ad0a41873`) include `estate.assign`, `estate.released`, move-in, relocation, and make-home actions. These change life-local estate/plot state; they do not write the household `homes` or `homeIndexes` maps. `server/routes/residence.ts` (SHA-256 `21beba152790209182533624f426d253905181958a6e6ed70dea7d0a879ccebc`) exposes location badges derived from the active life, not a home ownership record. Transient social `houses` are visitor/room state keyed by public character id, not residences. Therefore the household adapter must refuse missing home facts as it currently does. A later unit needs an explicitly allocated canonical home record/lifecycle owner and atomic hooks for allocation, ownership transfer/release, relocation/incarnation, and relevant scene revisions; deriving one from plot, LGA, `homeOwned`, or a badge would invent authority.

### Relationship authority

`SocialPlayerRecord` friendship/request/block maps in `server/types.ts` are keyed by publicId, not LifeId, and contain timestamps rather than a durable per-pair revision/source lineage. In `server/social/service.ts` (SHA-256 `d8532e16cfd49f5e3fd4df77804cbff3ba518ac3725a65c1800da3232da61e6a`), `friendRequest`, `friendAnswer`, `friendRemove`, `block`, and `unblock` mutate those maps. `cut` removes mutual friend edges and requests, and may enqueue unfriend effects; block invokes `cut`, while unblock only removes a directional block. `directoryStamp` is process-local cache invalidation, not durable pair revision. Existing friend timestamps cannot safely represent the required LifeId-scoped pair revisions or source A/B revisions.

The `pairFacts` household map has no non-test production writer. A later allocated unit must make social mutations and durable pair revision updates atomic in the owner transaction, define accepted/remove/block semantics (unblock must not recreate consent), and expose bounded exact-pair reads with protected read-set coverage. It depends on the canonical LifeId writer above; publicId-only friendship is insufficient.

## Current adapter and validation scope

The actual household service is internal and unregistered: `executeConsentCommand` in `server/households/durableService.ts` has no production route caller. Its trusted authority port is a transaction dependency, not a host-derived production implementation. `durableReads.ts` describes stronger life/home/pair facts than current production records can supply, so refusing absent or unloaded facts is the correct behavior until canonical writers exist. The current focused tests use fixture authority facts; they do not prove host/session-to-authority integration or enable public registration.

The adapter tests exercise a real Node store transaction and the production SQLite store adapter over Node's SQLite test storage, including commit/reopen/replay and rollback behavior. They do not exercise a deployed Cloudflare Durable Object, HTTP route, or real Worker runtime. Node persistence serializes and rewrites the full root JSON document on commit; it is not a row-level write. The Worker adapter uses keyed SQL tables and lazy map materialization, but the tested runtime is Node SQLite. Keep these claims separate from canonical authority and lifecycle correctness.

## Minimum future source ownership

1. Allocate an exclusive identity/lifecycle writer spanning `server/life-service.ts`, `server/host-context.ts`, `server/character.ts`, `server/world/service.ts`, and `server/accounts/service.ts`, with the two host compositions wired to that writer. It must atomically assign identity at creation and update locators/revisions on move, archive, adopt, park, restore, and erase. Preserve exact session/account binding and existing receipt semantics.
2. Allocate a canonical home authority owner before adding home-row writers. It must be tied atomically to real estate/ownership operations in `src/game/systems/estate.ts` and their server-side execution/receipt path; the existing household maps alone do not supply ownership authority.
3. Allocate `server/social/service.ts` for durable LifeId-pair revision/source writes at friend accept/remove/block/unblock and any character-erasure path, coordinated with the identity writer.
4. Keep route registration, financial liability consumption, and public activation separate. Until the same transaction has canonical life/home/pair facts and consumes every required liability handoff, refusal/abort remains mandatory.
