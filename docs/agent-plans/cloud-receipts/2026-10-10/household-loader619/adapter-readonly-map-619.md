## Existing transaction and once behavior

- Contract is `Store.transact` in `server/types.ts:839` and implementations `server/store.ts:478` and `deploy/sqlite-store.ts` (the latter exports `transact: (fn, options) => run(fn, options, true)` around line 864). Callbacks may be async. Node serializes them, operates on a private transaction view, discards it on throw, then applies it and awaits its durable file write before resolve by default (`server/store.ts:478-505`). Worker storage callback changes are accumulated in transaction-local maps and collections; `commit()` writes sessions, once receipts, collections and entry-layer writes inside `storage.transactionSync`, then the durable barrier must complete before the transaction resolves (`deploy/sqlite-store.ts`, transaction implementation and commit block around lines 640-710).
- `RouteContext.once/onceId` is defined at `server/types.ts:1176-1178`, built from `createOnce` in `server/routes/once.ts:88+`, and passed by both Node (`server/server.ts:514-525`) and Worker (`deploy/cloudflare-worker.ts:363-394`). `onceId` validates timed UUID IDs and receipt window. `once` fingerprints `(id,kind,request)`, returns a stored result with `duplicate:true` without invoking its closure, applies the existing per-session/per-server quota rules, and records successful results in the transaction (`server/routes/once.ts:121-151`). Thus an adapter service called only inside that closure can check a bound prior result before it loads household intent; a typed throw aborts the enclosing store transaction. Rejected `{ok:false}` results do not create once receipts. Node session `once` is inline; Worker maps it to `once_receipts` keyed by sender/id.
- HTTP request authority comes from `RouteRequest.session(db)`/`requireSession`, which calls host `sessionFor` on the transaction DB (`server/server.ts:362-372`; Worker equivalent around `deploy/cloudflare-worker.ts:659`). The session record has a cookie secret, public ID, cities and city life snapshots (`server/types.ts:74-100`); body data is not authentication. There is currently no public household route registered.

## Collection and bounded-key implications

- `Database` has an open `[collection: string]: unknown` extension slot, but no named households schema/property (`server/types.ts:743-777`). `ctx.collection(db,name,initial)` validates generic lower-case names and creates a collection on first write (`server/protocol.ts:287-295`); read code must avoid it because it creates state.
- `server/keyed.ts:122-134` `KEYED_SPECS` is the authoritative set of lazy maps. Adding household keys there is necessary for per-record access in the existing keyed layer. Node `server/store.ts` uses `Layer` and `KEYED_SPECS` for per-entry maps when configured in entries layout; legacy layout copies a non-session top-level collection whole on first access (`server/store.ts` file contract and view at lines 182-190). Worker default is legacy unless `STORE_LAYOUT=entries`; even in entries mode, a collection must be keyed/synced (`deploy/sqlite-store.ts:282-314`). It supports root plus per-map entry rows (`root:<name>`, `entries`) and includes them in one SQLite commit. Therefore an adapter promising bounded point reads needs an explicit fresh-install/migration/layout contract; merely storing a households map through generic legacy collection access does not prove a bounded database read.
- No household maps exist in `KEYED_SPECS`; present names include social, growth, civic, business, commerce, records, realValue, trustChecks, street, livingWorld. `households` schema, point read surface, read-set/protect rules, and write mapping remain unspecified pending the exact Integration port contract.
