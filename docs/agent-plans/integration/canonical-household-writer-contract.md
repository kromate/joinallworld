## Confirmed incompatibilities to correct in this unit

1. **Cross-city move is rejected by the pure plan.** e52 lifeIdentity.ts:269–280 requires unchanged slot.city and preservation of the old state/timestamp. Actual travel changes estate.city/state, then files the same record under the destination. readSlot additionally requires estate.city == slot.city. Reproducer: identified Lagos record completes an ordinary Lagos→Accra trip; inspecting it under the old slot after arrival yields slot_city_mismatch, while planning from a pre-arrival snapshot to Accra yields move_changes_city. Do not delete the city guard generically. Add a separate trusted canonical travel transition with the pre-mutation exact source snapshot, the same immutable identity/owner, validated destination city and post-mutation record; it permits the normal game transition and updates the locator atomically.

2. **A permanent one-LifeId-per-character index does not fit legacy switching.** AssignmentPlan expects characterIndex absent (lifeIdentity.ts:211–247) and proposes a single characterId/lifeId insertion, but a session may retain several distinct underlying records. Assign A, switch to legacy B, then make B's first authorized household mutation: absent-only insertion either refuses B forever or overwrites A's provenance. Define byCharacterLife explicitly before writing it. Minimal choice: exact (CharacterId, LifeId) association rows with validated composite keys; active authority still comes from the current pinned record, not this index. Retain A's association while B is active. Do not conflate these rows with consent CharacterIndex (hosted/joined/incoming). Lookup must be point-addressed; deletion must cover every already-assigned active/legacy/parked record through canonical containers and a documented reverse enumeration. No global player scan, silent legacy truncation or newly invented cap on existing saves. Current legacy containers are not proven uniformly bounded; report that honestly and bound the new operation's reads.

3. **Occupied slot exchanges need a batch transition.** planLifeIdentityMove requires empty destination and one source removal. swapLegacyLife exchanges two occupied slots, while fileCharacter may first archive an occupied destination. Build a bounded multi-record movement plan for these actual operations, checking all source references/identities, destination occupants, locator revisions and removals before any change. Preserve both identities; never sequentially overwrite an occupant or mint for it.

4. **Container moves and erasure have no locator maintenance today.** Account adopt/park/restore, expiry and unlink change session/archive addresses. A copied record retains identity but a locator containing the old secret becomes wrong. Update locators in the same existing transaction; account identity is not the life owner ID. Erasure needs a tombstone plus household termination/financial disposition before deleting canonical content. Unlink-with-retained-life must not terminate it.

5. **Home metadata cannot simply be appended.** cleanResidence and createLife would strip it. Add validated optional server-assigned residence identity/incarnation metadata and preserve it through current/away sanitation and travel. No creation in sanitize, GET, settle, world sync or constructor. A valid-looking client field is not authority: require the canonical binding row and exact owner-life crosslink. Corrupt metadata must refuse household authority without resetting the original home or minting a replacement.

6. **Stored dwelling and physical world address have different commit boundaries.** The household writer can canonically name the exact stored owned/rented residence from the main Store. It cannot certify a current world-shard plot allocation within that transaction using a previous shard read. Use address as descriptive data until its existing allocation acknowledgement is reconciled and pinned; refuse entry/use on an unresolved address. Do not add fake shard transaction methods or grant land/title authority.

## One next implementation unit: canonical assignment plus preservation

This is one cohesive server writer unit, not an additional pure model. The unit must connect the corrected plans to real Store drafts and existing lifecycle writers. Proposed function names are not existing APIs.

The assignment entry belongs inside the existing e52 executeConsentCommand transaction, after strict request parsing/authentication and replay probing, on the new successful authorized household-mutation branch. Refactor a synchronous transaction-local prepare/apply seam there; do not open a nested transaction. Assignment and the consent patch/receipt either all commit or all abort. The service currently requires an already-present actor proof before replay, so its new-intent branch must explicitly support an exact existing-unidentified current record; it may not solve this by minting inside sessionLife().

For an already-identified record, probe the versioned stable receipt using immutable actor character/life before mutable membership/home/current-location checks, following the separately reviewed A1 legacy contract. For an unidentified record, a purported old success cannot be reconstructed: no old-life inference and no speculative assignment to make a receipt match. Refusal or duplicate must leave IDs/homes/receipts unchanged. Keep once.ts unchanged.

Inside the callback:
- Resolve request.requireSession(db) without settlement or renewal needed for proof; retain exact device/account/session provenance. Require the explicit valid current pin, corresponding own CityLifeRecord, matching estate.city, valid stored salt and all normal onboarding/activity authority relevant to the command. Missing/ambiguous/corrupt rows refuse. Never call characterCity's newest fallback here. A body/header can assert an expected identity only; it cannot choose the authority record.
- Read exact record and existing identity, locator/association presence, selected owned or rented residence and canonical binding in this draft. For first assignment, generate opaque IDs with the existing server generator, check collision including tombstones by point lookup and construct a provisional plan. No ID derived from publicId, timestamp, LGA, furniture, account or salt.
- Assign only the acting exact life. An owner invitation must not mint the recipient's identity by reading their record. The recipient needs their own authenticated explicit household mutation to obtain identity; the eventual UI/API must expose that step without a GET migration. Do not quietly weaken recipient-life binding.
- Assign a HomeId only to the exact retained dwelling selected for explicit registration. A currently-away unregistered dwelling cannot acquire a fabricated current-room snapshot: require the actual home scene to have been captured from its canonical residence first. Existing bound away/parked homes remain resolvable without owner presence.
- Keep estate.home, all existing current/away residence fields, inventory, cash, action/once history, salt and gameplay progress intact apart from the explicitly added metadata and authorized command effects. Original-home/return references are separate from effective household selection.
- Compare every canonical supporting source and absence expectation again before applying: record identity/reference, session/device/account binding, location/locator, residence metadata, home/scene revisions, index rows and all consent read-set entries. Persist metadata, canonical life/home facts and indexes with the actual patch and receipt in this one Store transaction. Unknown write failures propagate; no partial success or best-effort backfill.

Preservation is mandatory in the same unit, because ordinary play can immediately invalidate an assigned identity. Add an explicit transaction-bound canonical-writer dependency at existing shared lifeAuthority composition and its direct character-move callers; it must receive the current Db draft from the owning transaction, not capture a process-global “current DB”. Wire it through the existing mutation callers; a WeakMap of state-to-session alone is insufficient. New IDs remain exclusive to the assignment callback. Preservation hooks may move an existing locator or update scene/home state during settlement without creating any new identity.

Cover ordinary settlement/arrival and action-triggered arrival, world rekey, social ping, normalize/swap, account container moves, archive and deletion. Before travel/refit, capture only the bound home's permitted scene/capability snapshot. After cosmetic/furniture changes, update scene revision; before relinquishment/replacement, retire its incarnation and invalidate/close its household, rather than retargeting. Main-home selection alone preserves individual bindings. These hooks must use the owning Store transaction, not the asynchronous world watcher.

The finite writer may first land inactive with source/tests and actual Store persistence evidence. **No public household registration/invitation/acceptance activation until the existing closure/removal path and mandatory liability handoff can complete.** e52 currently refuses every patch with liabilities; accepted membership followed by leave/revoke is therefore not a safe enabled slice. Empty-liability behavior may not be invented by assuming no money exists. Resolve it against a canonical, explicitly empty/no-liability state or implement the actual consumer before membership activation. Erasure cannot delete pending liabilities or block legitimate privacy erasure indefinitely as the shipped behavior.

Owner allocation: one existing Cloud integration writer owns this unit, including necessary shared types/host composition/account/character edits. Foundation/shared files require Root's explicit serialized allocation. No second writer and no parallel edits to shared startup files. Narrow intended edit set: households lifeIdentity/storage/read/service plus one canonical writer module; server/types, src/types/life and estate sanitation; shared host-context/life-service/character plus the direct world/ping/core/account/archive call sites required to pass the same transaction context. Host server/Worker composition changes are only dependency wiring. Do not alter general Store or once semantics, unrelated Business, Family, money rules, prices, routes or startup budgets. The owner must enumerate exact affected ctx.settle/act call sites before coding; any missing canonical mutation seam is a blocker, not permission to fall back to an asynchronous repair.

Run remotely on the actual implementation SHA, through real normal Node HTTP/file Store and actual Worker HTTP/persistent SQLite; no mock authority maps, direct life funding, fabricated home facts or alternate receipt implementation.

1. Create normal consenting actors through existing session/onboarding flows and real current homes. GET/settle/refused/wrong-actor requests leave identities absent. 3. Exercise action-triggered and timed arrival, plus a destination with a retained old life. Snapshot comparisons exclude only legitimate travel/game effects and new metadata.
4. Use the real legacy switch endpoint A→B→A: different LifeIds, unchanged publicId, both locator associations retained, exact receipts survive, neither life inherits the other's household rights. Existing legacy saves are preserved.
5. Use genuine account adopt/park/switch/restore/unlink flows and reopen: secrets/containers may change, immutable identity and original homes do not. An erased life is tombstoned and cannot be replaced by the latest life. Authorized account deletion must complete its required terminal cleanup.
6. Exercise existing ordinary home actions: main-home selection, owned/rented switch, replacement, relocation and upgrade. Verify incarnation retirement vs scene-only changes, no private content leak and no stale use after mutation. Away projection must be captured before refit, not synthesized from the owner's later room.
7. Before any member activation, demonstrate actual accept → permitted member-only use → owner revoke/member leave → safe public egress and durable original-home return offer on both hosts, including restart. This is a later acceptance gate on the complete consumer path, not evidence this prerequisite review supplies. Rent remains disabled until the contracted liability/payment state machine exists.

Pass the same draft to every writer and let errors escape. No whole-save rewrite or separate post-commit identity persistence.
