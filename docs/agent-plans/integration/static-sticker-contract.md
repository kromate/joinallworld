## Existing behavior that this slice must extend

- Composer.vue already has independent emoji insertion, actor/conversation-scoped text drafts, picture choose/preview/explicit-send and generation checks. It has no attachment-panel abstraction to assume. Picture/voice upload routes and stores are separate and are not needed for stickers.
- MessagesApp.vue supplies the current thread, title and sender; it clears replies/previews on actor changes. socialClient.ts:343–374 delivers and retries outbox entries under their original clientId. Its deliver function has no local generation check around the awaited result; a new sticker path must add one, not assume Composer's picture guard covers it. resetSocial clears outbox/state, but that alone does not fence a late completion.
- server/routes/social.ts:74–90 wraps social service operations in the real durable Store transaction and delivers after commit. HTTP /api/social/messages and dm-send share service.send.
- service.ts:1519–1609 currently finds retained messages by sender/cid. Replay compares text/sendHash and voiceHash, not a complete intent. Reply target/mentions are not part of that comparison. History is capped at 200 (with up to three protected pins); trimHistory deletes older rows. A retry after its original row is trimmed is not protected by that lookup.
- memberConv requires both canonical membership and the player's conversation index. DM block rules use blockedEither for new sends; group visibility is viewer-directed via visibleTo. Do not advertise symmetric group suppression that the source does not provide.
- messageView, summary/bodyOf/quoteText, pinProjection, updateMessage and growth/message-push all construct different projections. Adding only a bubble renderer would miss privacy, replies, unread previews and notifications.
- updateMessage uses the existing once helper, retains sendHash on edit/delete, clears media and reactions, updates reply quotes and removes pins. It currently forbids editing images/voice but would accidentally permit a new sticker unless explicitly amended. Forward currently allows only text; a new sticker must be explicitly excluded if forwarding remains text-only.

## Catalogue and privacy decision

App-supplied asset IDs suffice for the artwork in this slice: every permitted sticker is public first-party static content already distributed by this app, not a private uploaded file. **The fact that a person sent one, its author/thread/reply/time/pin state, remains private message data.** A public asset URL never grants conversation access. Removing a message cannot revoke a copy of public artwork or an already seen screenshot; it must remove the private message occurrence/projection.

Introduce a small authoritative shared catalogue, proposed `src/game/content/stickers.ts`, containing immutable ID, catalogue version, plain-text label/alt, dimensions and enabled-for-send status. Server accepts only exact IDs in this catalogue. Client asset URLs come from a separate fixed import manifest in the lazy Messages feature, never concatenation of a request-provided URL/path. Store only catalogue version/ID in a message, not SVG/HTML/base64/remote URL. No third-party search, uploads, discovery, pack subscriptions, telemetry integration, payment, media database or public personal-data endpoint.

Initial pack: six original first-party reactions such as Hello, Thanks, Nice one, Okay, On my way and Laugh. Artwork remains an implementation deliverable, not supplied evidence here. Each static WebP/PNG <=24 KiB, maximum intrinsic 512×512, total pack <=144 KiB; smaller is preferred. No animation, scripts, external fonts or SVG active content. IDs are versioned and never reused for different art. Keep decoding old IDs even when sending an item is disabled. If an asset must be withdrawn, show a neutral “Sticker unavailable” placeholder; do not reinterpret its ID.

Do not silently make stickers subject to the existing “pictures: nobody” upload preference: that preference concerns player-uploaded pictures. Curated stickers follow ordinary message permission/rate/stranger limits, like emoji. Say this plainly in the picker (“Allworld stickers”). No new permission prompt is needed. Existing block/mute/report controls apply. If product later intends an independent sticker preference, that is a separate explicit change, not inferred from a media key.

## Request, replay and compatibility

Extend SendMessageBody with a discriminated sticker variant, while preserving the existing text shape byte-for-byte:
```ts
type StickerSend = {
  conv: ConversationId
  clientId: TimedId
  body: ''
  sticker: { version: 1; id: StickerId }
  replyTo?: number
}
```
First slice sends only into an existing visibly named thread. Provisional to: direct chats must first be opened by the existing normal chat flow. The sticker variant rejects to, caption/nonempty body, mentions, forward, image/voice fields, unknown sticker keys and mixed content. The existing server-only picture/voice media argument cannot be combined with it. HTTP and dm-send must take the same validation/service branch. An older server sees an empty body and must refuse rather than accidentally post a text label.

New sticker sends use timed IDs from existing newClientId and ctx.onceId. Existing text IDs and old text/voice fingerprints retain their current behavior. For stickers, use a separate `message.sticker` receipt kind and a versioned SHA-256 fingerprint of a fixed-order array:
`['sticker-send-v1', actorPublicId, convId, catalogueVersion, stickerId, replyToOrNull]`.
Do not hash a rendered label, fetched asset bytes, mutable target name or post-send quote text. A short prefix plus SHA-256 fits the existing once limit without hash53 reduction.

Store a minimal successful receipt `{ok:true, format:'sticker-send-v1', conv, seq}` through ctx.once in the same social transaction as append. Do not store a private conversation/message projection inside the receipt. Keep a versioned sticker intent marker/hash on the MessageRecord through deletion, even after the visible sticker reference is removed. No new receipt store is required.

Authorize current access before returning any replay projection: prune an expiring house conversation through the existing house lifecycle, require canonical membership/index, enforce DM block refusal, then probe/execute once. A retained successful receipt after a block/removal/visit expiry cannot disclose old or fresh conversation data. After duplicate detection, project only a currently accessible stored row; if trimmed, return a minimal “previously sent; no longer in history” acknowledgement with no re-append or invented message. Unsent rows return their current tombstone, never the old sticker. Expired timed IDs refuse even after the receipt is pruned.

**Cross-format collision guards are required in both directions.** Before a new sticker receipt, reject a retained legacy message with the same actor/cid in that target rather than adopting its text/voice outcome. A legacy text/picture/voice send must reject an existing sticker marker with that cid. When the sticker message has been trimmed, a point lookup of the same actor's retained once receipt must still prevent a legacy send from reusing that sticker intent ID. Implement this narrow guard in the social service against the existing receipt row representation; validate own data/keyed semantics and exact kind, never return its stored result through the legacy path. Do not enumerate receipts or rewrite the general once helper. Absent/unrelated legacy rows retain their old behavior. The service's original per-conversation legacy replay semantics are not upgraded by this contract.

A new client ID after uncertain delivery is not a retry. Keep the exact frozen target/sticker/reply/id until delivery is reconciled or the player explicitly discards it. Altering a sticker or reply while a request is pending must not mutate the retry body. No automatic resend on reconnect, expiry, actor switch or changed membership. Cross-format reservation is bounded by the retained message/once evidence; this does not promise indefinite reservation for legacy non-expiring text IDs after all evidence is pruned. An expired sticker request itself always refuses through onceId.

The trimmed-history acknowledgement requires an explicit transport union: add a `code:'sent-retained'` success with only `{receipt:{conv,seq},duplicate:true}` to the sticker HTTP result. For WebSocket, retain the existing `dm-sent` frame type but define a disjoint minimal-receipt variant with `retained:true`, `receipt`, `clientId` and `duplicate:true`, without a fabricated conv/message projection. Update server/ws/social.ts:137–142 and client frame handling to branch on that variant, confirm only the matching scoped outbox entry, and never pass it to noteConv/mergeMessages. This is a concrete additional writer allocation discovered from the actual socket handler; the inventory's no-ws-edit assumption cannot cover retained receipts. Verify the protocol guard/tests without broadening the wire type whitelist.

Add message.sticker to LIGHT_KINDS only via the serialized shared-file owner; do not change quotas, retention, classification of existing kinds or monetary paths. This is a required review gate before implementation, not permission to edit the shared helper concurrently.

## Message lifecycle contract

- **New send:** same onboarding/social reachability, mute/suspension and ordinary message rate/stranger safeguards as text. The catalogue is server-authoritative; selecting a local image grants nothing. No extra user charge, transfer, provider traffic or paid storage.
- **Membership/revoke:** group removal, leaving, DM blocks and expiring temporary house visits retain their existing authority rules. No sticker feature extends a visit or Family permission. All history, live pushes, pins and replies are projected through the same visibility rules. Group block direction remains exactly the existing model unless separately reviewed.
- **Delete for everyone:** sender-only existing update permission/version/once guards. Remove sticker from public projection, keep the nonrenderable intent marker, clear reactions/quote and pins, update dependent quotes to “Message deleted,” and broadcast only authorized current tombstones. Shared catalogue assets are never deleted by an individual unsend.
- **Edit:** stickers cannot be edited into text or another sticker. UI hides Edit, server explicitly refuses it. A different sticker is a new explicit send.
- **Reply:** supported. Quote uses “Sticker: <catalogue label>” derived by server, only if source is currently visible/nondeleted. No thumbnail/raw asset link is copied into reply metadata. Existing sender-block filtering and source-delete quote cleanup apply. Chosen reply seq is part of sticker intent, even if the source later becomes unavailable.
- **Forward:** first slice explicitly keeps forwarding text-only, matching current media behavior. Hide Forward for sticker messages and add server rejection to prevent forwarding their fallback label as if it were original text. A person may independently select the public sticker in another thread; that is a new explicit message, not source access or forwarded authorship. Future forwarded-media behavior remains separate.
- **Pins:** valid visible stickers are pinnable under existing DM/group-owner rules and three-pin cap. Extend server global eligibility, client canPinMessage, pin frame validation and both collapsed/full pin renderers. Deleted/withdrawn/unavailable occurrences cannot leak through pins; reconcile stored pins in existing bounded conversation mutation/cleanup paths. Scope/revision fences are unchanged.
- **History/prune/account cleanup:** trimmed/deleted/private-message metadata follows existing social retention and erasure. No per-message asset objects accumulate. Receipt metadata retains only the existing once window; a replay never restores a trimmed or erased message.
- **Previews/push/report:** bodyOf/summary/quoteText and unread/outbox fallback display “Sticker” or its safe label, never blank body or markup. Native push remains “Sticker,” with existing hidden-preview/mute/quiet-hours/blocked/member checks and no image URL. Existing player/conversation report can include safe sticker labels in evidence; no media upload report/store is added.

## Actor, draft and network fencing

Sticker selection is local ephemeral state. Preserve the user's unsent text; sending a sticker does not implicitly send or clear that text. Keep no persistent sticker outbox for this slice. Cached public asset bytes can be shared across actors, but selected sticker, reply, target name and pending intent cannot.

Separate the shared client's non-reused **actor epoch** from the composer's **thread/picker request generation**. Actor transition/reset, including A→B→A and auth loss, invalidates shared async work. Thread switch or local component disposal invalidates only that component's selection/preview/intent work; it must not rotate the shared actor epoch, drop legitimate overview work or strand global loading/dirty flags. Capture actor epoch + exact conversation + immutable intent at selection/send. Verify the appropriate scope before draft/outbox/thread writes, toasts, rekey or reply clearing. Preserve the existing X-Allworld-Actor authenticated transport; actor-string equality alone is insufficient.

**First prerequisite: shared social actor isolation, before sticker changes.** [The complete audited contract](social-client-actor-fence-contract.md) covers every shared-client await/timer/socket/listener path, including loadPeople/loadMoreFriends, perform callbacks/toasts/follow-up sync, profileVersion, flag ownership, reentrant reset, navigation and canceled-but-queued timers. Actual src/client.ts already rejects old-actor payloads; this source finding is a late-side-effect gap because social call catches that rejection as a normal failure. It is not a reproduced private-payload leak. Same existing ONLINE writer gets a finite three-file unit: socialClient.ts, socialClient.test.ts, and ONLY removal of the brittle reset-start regex/unused source read in src/game/social.test.ts, preserving its other checks. Root expressly allocated that test exception. No shared types/receipt list or server changes in this first unit. Frozen deferred A→B→A tests must prove old completions cannot clear replacement flags, toast, create replacement requests, expire/rekey/confirm its outbox or alter its socket; same-actor thread switches must still permit legitimate global completion. Source review and exact raw focused tests precede the broader sticker allocation.

Membership/house expiry/DM block authoritative updates disable send and clear the sendable selection. A delayed successful response cannot re-enable controls or restore stale thread contents. An aborted network request may already have committed: show “Delivery not confirmed” rather than “not sent.” Retry is manual under the unchanged intent. Offline may show cached catalogue/selection; Send is disabled while disconnected, with an explicit explanation. Reconnect refreshes authority; it never sends automatically. Rejected/expired retries do not create a new ID.

## Three UI sketches and selected direction

These are design alternatives, not rendered prototypes. They reuse current colors/type/rounded controls rather than redesigning the phone.

| Option | Concrete interaction | Tradeoff |
|---|---|---|
| A — combined emoji/sticker popover | Existing smile button opens tabs “Emoji / Allworld stickers”; a six-item labeled grid selects a sticker; a preview row appears above the composer with “Send to <thread name>” and Cancel. | Least toolbar crowding at 320px, preserves text and current context. Recommended. |
| B — bottom sheet | A dedicated Stickers button opens a modal sheet with visible destination, larger grid and preview; Send remains in the sheet. | Strong focus boundary and recognition, but covers the thread and adds another toolbar control. |
| C — inline expandable tray | A text “Stickers” control expands a small grid beneath the reply row; selected sticker remains beside explicit Send to <name>. | Thread remains visible and focus is simple, but consumes more vertical space with the keyboard. |

Choose A initially: existing EmojiPicker provides an established entry, while picture preview already establishes choose-then-send. Do not make tapping a grid cell send. Keep a named destination beside the explicit send button, updated only from current thread authority; long names wrap. A selected sticker has a visible outline and label; selected-state appearance is not the only confirmation.

All actionable targets at least48px; 320/390 layouts without horizontal overflow; no hidden composer/reply under soft keyboard. Keyboard Tab/arrow navigation, Enter/Space select only, explicit focused Send activates delivery. Escape closes the picker and restores the triggering button; a modal variant would need focus containment. Screen reader labels include sticker meaning and send destination; selected preview does not duplicate decorative alt speech. Loading/error status uses polite live announcements; critical refusal uses an alert. Static artwork/no autoplay; sufficient contrast in light/dark mode. Current existing 32/36px ancillary controls are not evidence this requirement is already met.

Primary reference notes supplied by Root: [Telegram sticker panel/editor](https://telegram.org/blog/sticker-maker?setln=en) and [Signal stickers](https://support.signal.org/hc/en-us/articles/360031836512-Stickers) were fully read by Root. [WhatsApp sticker help](https://faq.whatsapp.com/639351827594474/?cms_platform=web&locale=en_US) was only supported by a search snippet; its opened page yielded zero lines. This review did not browse or observe those UIs. The alternatives above are inferences, not borrowed artwork, encryption claims or implemented prototypes.
