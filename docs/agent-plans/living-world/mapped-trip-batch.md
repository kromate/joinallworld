# Mapped trip service batch

This batch adds the server-side persistence/control adapter needed to connect an accepted mapped route to the existing starter permission and finite fleet contract. It is deliberately not registered in the route table and does not enable mapped driving. The default constructor has neither a physical resolver nor a motion verifier, so `current`, `start`, `input`, `pause`, `resume`, and `recover` fail closed with `physical_evidence_unavailable`; no fleet row or trip record is created. Both optional dependencies are trusted server-code seams, never HTTP fields. Synthetic fixtures exercise service mechanics only and are not physical acceptance evidence.

The adapter reuses `readValidatedQualificationRecord`, `readDrivingQualificationEvidence`, `readValidatedStarterRentalRecord`, `allocateFleetUnit`, `revalidateFleetLease`, `returnFleetUnit`, `createDriving`, `readValidatedDrivingState`, `stepDriving`, and `pauseDriving`. A start derives current actor/city/location, qualification, and starter permission inside the store transaction, then requires a resolver result bound to that actor and location. Every accepted result must include the full route/checkpoint structure and named source hashes for the pinned manifest, tile, pack, route clearance, depot site, vehicle descriptor, boarding/exit, actor envelope, terrain support, and yield policy. The service validates shape, bindings, time freshness, checkpoint order, and hashes' syntax; the trusted resolver remains responsible for establishing what those hashes mean and verifying the physical evidence itself.

Trip records are per public actor and contain only the server-simulated motion state, revision/sequence/credit, fleet unit reference, route version, and proof pins. The shared fleet contract is stored once under `livingWorld.fleet`; public views never enumerate it or expose other renters. Controls accept bounded throttle/brake/steer frames only. Position, checkpoint completion, stop evidence, and return pose are derived from the server's fixed 100 ms simulation. Every candidate frame also needs a fresh trusted motion-verifier response bound to the actor, trip, route, proof pins, time, exact server-derived before/after states, allocated unit, lease generation/start revision, and fleet revision. The server freezes the verifier's independent input copies, compares the result against a separate pre-callback snapshot, then rechecks time, current qualification evidence, and lease validity before committing. A missing, refused, stale, or failed verification pauses the trip without saving candidate movement or releasing custody. The last authored stop must be the depot return checkpoint before the service can release fleet custody. Reconnect never resumes held input. Qualification/permission or route/depot invalidation moves the trip into stopped recovery without releasing the vehicle.

## Production integration blockers

At the source revision used for this batch, `server/living-world/district-sweep.ts` is explicitly geometry-only and reports `routeAuthorized: false` and `canBoard: false`. Its own limitations leave vertical support/elevation, road crossings and yielding, and doorway/actor entry/exit unverified. Existing `vehicle-boarding.ts` and `depot-site.ts` also keep the physical gates false. None can be passed to this adapter as accepted evidence. A production resolver must bind and verify the accepted route, depot/boarding volume, street-sedan source geometry, actor path/volume, authored terrain support, and traffic/yield policy from current server assets/state. A separate production motion verifier must prove the complete moving vehicle footprint per step against current physical evidence. Both must be absent/refuse until their required checks pass.

This batch does not offer or settle a parcel. The next delivery slice must consume the server-owned checkpoint indices and state from this record, then use `parcel.ts` transitions with trusted stopped poses constructed by the server. The existing NPC restock service is still not registered in production routes; it requires the real synchronous fixed simulated-cash wallet action in the same transaction. Neither the test resolver nor a stopped checkpoint index is permission to create a live mapped delivery.

Privacy helpers are actor-scoped. The summary reader never lists fleet members. Erasure refuses if any retained shared fleet lease names the actor; `fleet.ts` currently preserves actor identity even after return. A future approved anonymous fleet-watermark migration is required before privacy erasure can remove that retained identifier safely. The recovery endpoint currently only records/acknowledges stopped recovery; it does not move or return a vehicle. Recovery exit needs separately reviewed server-owned stopped-depot evidence and fleet-watermark handling.

## Acceptance for this adapter

- With the production default resolver absent, current/start do not create fleet or trip rows; a browser-supplied proof, position, completion flag, reward, or wage is impossible under the exact request schemas.
- Test-only resolver and motion-verifier fixtures exercise start, per-frame candidate checks, same-packet replay, changed-packet conflict, timeout/clock stops, pause, reload-stop, resume, and retained recovery. Tests must be described as adapter fixtures, never mapped-physical acceptance.
- Five actors racing for the four fixed units produce at most four leases. Each lease, actor record, and once receipt commits atomically; a failed durable write leaves none of them.
- Missing course evidence, permission revocation, route unavailability, refused whole-vehicle motion verification, clock reversal/timeout, stale sequence/revision, malformed/future saves, and another actor's trip ID cannot advance motion or release custody.
- Final return can only be derived after the accepted route's server-simulated depot stop and verified motion frames; parcel offer/collection/delivery and the real rendered mapped-world journey remain later gates.
