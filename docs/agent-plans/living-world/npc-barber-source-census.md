## Persistence, terminal CAS, and privacy

- Current actor barber data is under `livingWorld.barber[publicId]`, with strict `readValidatedBarberRecord(value, publicId)` and exact lesson/result schema (barber-service lines 23–33, 86–124). The appointment should not overload the mannequin `results.basic/advanced` fields: their reader intentionally requires those exact fixed looks and lesson IDs.
- Use a separate versioned appointment field/record with a monotonic revision and terminal appointment/result witness. `ctx.once` request receipts are useful for same-request retries, but the retained terminal row must be the durable fence against new request IDs and receipt expiry. CAS must cover both actor appointment revision and the shared NPC reservation/appearance revision; otherwise two distinct request IDs can race to haircut/pay the same NPC.
- `server/living-world/privacy.ts` includes `barber` in its bounded living-world slices (line 12), exports only a whitelist summary (lines 53–58, 97–101, 149–175), rebinds a validated barber row for the same character by changing only `account` (lines 227–243), and erases rows for proven actor IDs through `eraseLivingWorldProgress` (lines 293–329). `server/accounts/service.ts` invokes the rebind on retained guest conversion and calls erasure for delete-account, preserving the current active actor only when `erase:false` (lines 512–524). Any actor-private appointment/receipt fields need corresponding strict reader, account rebind, export whitelist decision, and erase behavior. A shared NPC appearance override is world state, not the account's private receipt; account erasure should remove the actor receipt without leaking its consent or appointment details through exports, while not silently reverting a completed shared haircut.
- Keep a clear row boundary: actor-private consent, quote, revision, and paid terminal witness are keyed to `publicId` and owner-checked; the current shared NPC appearance is keyed by authored NPC id and version and contains only the approved public appearance delta. Atomic host commit applies both with the canonical wallet action in one `ctx.store.transact`; refusal, expired/revoked consent, NPC departure, style/version change, stale revision, failed payment, or storage failure commits neither.
