# Proposed NPC barber appointment domain — source-only, not integrated

Baseline: `eec14690544a4646e4cd8a5ad280d61bbe2709ca` in the Integration checkout. The files under `src/game/living-world/` are a proposal bundle; no application or service source was changed and the tests were not run.

## Bounded outcome

Offer one version-1 fictional NPC barber appointment per player actor. The offer is server-authored and already carries NPC approval for one exact preview and the proposed fixed simulated payment of 80 game cash. The player explicitly accepts it, then completes the existing bounded barber tool plan under a fresh session. A valid completion produces one terminal result and one immutable proposed effect: apply the approved low-cut look to the NPC and credit the player 80 simulated game cash. No real player's look or wardrobe is written. Current source has no authorized NPC appearance writer or renderer, so the host must not apply or advertise a visible NPC change until GRAPHICS defines that seam.

The only proposed look is `man-low-cut-v1` for a male NPC. This identifier is supported by the existing basic mannequin plan and `APPEARANCE.hair.man` (`low-cut`); that proves the catalogue style exists, not that it is approved for an NPC model. The fixed customer id in this draft is a proposal identifier, not a customer found in published NPC content. GRAPHICS must approve the actual customer instance, model/body compatibility, preview rendering, and server-owned appearance read/write authority before issuance.

The proposed 80 payment is the bounded policy decision from Sol for this one service, not an existing appointment price or live economy. Existing basic mannequin practice pays 80 and starter clippers cost 120; a zero-cash/no-debt actor could have 160 gross after one basic claim and this appointment, leaving 40 after the tool purchase, subject to existing debt repayment. No balance boost, debt exemption, real-money value, or `social.earned` mutation is proposed. The pure fixture constant does not activate the payment.

## Domain boundary

`barber-appointment.ts` makes the actor, fictional customer, catalogue version, complete before-look fingerprint, exact approved preview, fixed payment, NPC consent generation, issue/expiry times, practice session, and terminal result explicit. It accepts only a trusted server-authored offer; the caller must derive the consent, current look, presence, revocation generation, practice session and completed practice from authoritative state inside the store transaction. Browser input is limited to accepting the exact displayed terms and the bounded controls already handled by `barber.ts`.

`finishBarberAppointment` returns an immutable proposed effect only on the first valid completion. The host must commit the NPC appearance update, fixed 80 wallet credit through a server-only action, and terminal appointment together in the same durable transaction. Use `ctx.once` for request retries and a durable per-actor terminal record so a new request id cannot create another appointment or payment. A failed appearance write, wallet action, or durable commit must roll back all three. The pure module does not provide that atomicity.

The persistent adapter should keep exactly one appointment generation for each actor and never replace the terminal row after receipt expiry. It must bind the appointment to the existing barber account owner, include the row in account adoption/parking/archive/export/erase handling, quarantine malformed rows unchanged, and preserve a terminal watermark until the account's verified erasure. A single shared NPC also needs a server reservation/CAS so two actors cannot consent against the same old appearance and both commit; departure, revocation, expiry, or changed appearance cancels without pay. The source creates an initial version-1 offer and refuses reissue only when the host retains that actor-keyed row; `ctx.once` alone is not enough after its receipt expires. The server route must enforce one version-1 appointment per actor and one active reservation per NPC. A reset/new appointment requires a separately reviewed generation policy.

The active appointment practice must use a fresh server-created session bound to this appointment. Do not treat the existing mannequin claim or its retained `NpcResult` as service evidence. A claimed mannequin lesson cannot also pay the appointment amount, and the appointment payment cannot be emitted by the mannequin lesson claim. The adapter must reject public request fields such as `practice`, `completed`, `look`, `styleId`, `amount`, or `price`; it reads the actor-bound persisted appointment practice only. A syntactically valid complete `BarberPracticeState` is not proof of provenance: the pure parser validates shape and plan, not who wrote that value. The pure test deliberately demonstrates this boundary instead of falsely claiming to reject a structurally plausible forged save.

## Existing boundaries and unresolved owners

- `server/living-world/barber-service.ts` owns current actor/account/city/location checks, `ctx.store.transact`, `ctx.once`, pause/reload, and the mannequin `ctx.act` call. It stores only `livingWorld.barber` and currently has no appointment row.
- `src/game/systems/living-world.ts` owns the existing server-only barber lesson reward and tool debit. The proposed appointment payment needs a distinct fixed server action/ledger label, using the canonical wallet/debt behavior; no direct cash writes.
- `server/keyed.ts`, `server/living-world/privacy.ts`, and `server/accounts/service.ts` own collection layout and account lifecycle/privacy. Sol owns any shared changes there.
- `server/routes/living-world.ts` registers mannequin routes only. Sol owns a future appointment route and protocol types.
- `src/game/systems/onboarding.ts` changes the current player's look and wardrobe; it is not an NPC appearance API and must not be repurposed.
- `src/app/features/living-world/BarberApp.vue` owns current mannequin interaction. APP UI owns any appointment client work; it must show exact NPC terms, consent state, cancellation and retained results without implying a real booking.
- GRAPHICS owns approval of the NPC instance and render/appearance authority. Until that contract exists, the proposed effect stays adapter-off; this bundle does not claim a rendered NPC appearance outcome.

## Proposed pure test cases

The new test file uses the existing control engine to produce a complete basic plan, rather than seeding a complete result. It covers supported style mapping, same-slot accessory rejection, strict reload/corruption, stale revision and monotonic-clock refusals, changed appearance/revocation/expiry, incomplete practice refusal, one completion effect, precommit departure/change, and terminal replay with no second effect. A structurally valid terminal practice object is intentionally not described as forged by the pure domain; only the HTTP host can prove that such JSON never replaces the server-owned session.

Required production tests must prove: a zero-cash actor completes the existing basic mannequin lesson and separately completes a fresh appointment session for exactly 80 through the canonical wallet action; both payments are once-only and existing debt repayment remains active; the previously claimed mannequin session/result cannot be reused as appointment evidence or paid again; public `practice`/`completed`/`look`/`styleId`/`amount` fields cannot alter the actor-owned record; two actors cannot reserve/commit the same NPC generation; response loss, stale CAS, appearance/write/wallet failure and restart preserve all-or-nothing state; account adoption/park/restore/export/erase preserve the new record correctly; and Worker/Node/browser tests show the exact preview and result. The current source has none of this appointment host or rendered customer acceptance.
