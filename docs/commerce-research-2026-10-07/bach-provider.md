## Provider API surface relevant to Allworld sellers

Official Bachs API docs list the REST resources for checkout sessions, connected accounts, payments, refunds, payouts, payout destinations, balances, transfers, and reference data ([API reference](https://docs.bachs.io/api-reference/overview)). The documented production/sandbox bases are `https://api.bachs.io` and `https://sandbox-api.bachs.io`; the source uses the same bases ([client.ts](/Users/anthonyakpan/Desktop/go/gm/backend/functions/src/payments/bachs/client.ts#L109-L119)). Configuration names observed in Goalmatic source are names only: `BACHS_API_KEY`, `BACHS_WEBHOOK_SECRET`, `BACHS_SANDBOX_BASE_URL`, `BACHS_BASE_URL`, `BACHS_SANDBOX_API_KEY`, and `BACHS_SANDBOX_WEBHOOK_SECRET`. Their values were not read.

For the requested earnings-only scope:

| Capability | Official endpoint/operation | What it means for Allworld | Goalmatic status |
|---|---|---|---|
| Merchant/connected account | `POST /v1/accounts`, `GET /v1/accounts/{id}`, `POST /v1/accounts/{id}`, account links/capabilities | Onboard a seller/payee and request recipient or merchant capabilities. | Not implemented in the inspected Goalmatic Bachs adapter. |
| Checkout/collection | `POST /v1/checkout-sessions`, `GET /v1/checkout-sessions/{id}` | Buyer pays for a seller/world item through hosted checkout. | Implemented for Goalmatic billing and marketplace purchases; seller-specific routing is not established. |
| Balance | `GET /v1/balances` | Read the Bachs balance from which withdrawals are funded. | No Goalmatic wrapper found in `payments/bachs/client.ts`; provider capability only. |
| Withdrawal destination | `POST /v1/payouts/destinations`, `GET /v1/payouts/destinations`, `GET/PATCH/DELETE /v1/payouts/destinations/{id}` | Register and reuse a seller’s approved bank/mobile-money destination. | Not implemented in the inspected adapter. |
| Withdrawal/payout | `POST /v1/payouts`, `GET /v1/payouts/{id}`, `GET /v1/payouts` | Withdraw seller earnings; use an idempotency key and track asynchronous status. | Not implemented in the inspected adapter. |
| Cross-currency withdrawal | `POST /v1/payouts/quotes`, then payout by `quote_id` | Quote before paying out to a destination in another currency. | Not implemented; do not assume NGN can fund every route. |
| Refund | `POST /v1/refunds`, `GET /v1/refunds/{id}`, list/by-charge | Return collected buyer funds, separately from seller earnings. | Implemented for existing Goalmatic transactions; not an Allworld seller policy. |
| Webhooks | Endpoint registration plus `collection.*`, `payout.*`, `refund.*` events | Server-authoritative collection, payout, and refund state. | Goalmatic verifies HMAC signatures and deduplicates event IDs for its billing webhook; no payout event handler exists. |

The official [withdrawal API guide](https://docs.bachs.io/guides/payouts/payout-using-api) documents the short NGN path: register a destination, check `is_usable`, then `POST /v1/payouts` with destination and decimal-string amount. Fees are charged on top, and `total_debited` is the balance impact. Payouts are asynchronous (`pending`/`processing` → `completed`/`failed`); `201` is acceptance, not proof of money received. Every money-moving POST needs a stable idempotency key. The [withdrawal overview](https://docs.bachs.io/guides/payouts/overview) adds prerequisites: valid API key, payout-enabled organization, funded balance, identity/account information, approved destination, and supported currency/method.

For a marketplace model, Bachs documents two distinct choices. The platform may withdraw its own balance, or use Connect: create a recipient account with `recipient.capabilities.payouts.requested` and `transfers.requested`, submit the holder and payout destination, fund that account with a transfer, then call payouts while acting as that account. A recipient account does not collect payments directly; direct seller collection requires the longer `merchant` configuration. This distinction matters for Allworld: decide whether sellers earn from a platform-held settlement ledger or receive direct Bachs collections. Do not represent a transfer-funded balance as a settled sale without an Allworld ledger and reconciliation record.

Official refunds are separate from withdrawal. Bachs says refunds are full or partial, asynchronous, and require a prior payment plus a webhook endpoint; `POST /v1/refunds` creates the request and `refund.*` reports the outcome ([refund guide](https://docs.bachs.io/guides/refunds)). Bank-transfer refunds may be unavailable for NGN while cards and some mobile-money rails support refunds; the exact method/currency matrix must be applied per checkout.

## Webhook and go-live requirements

The official [webhook guide](https://docs.bachs.io/guides/webhooks/overview) requires a publicly reachable HTTPS POST endpoint, a Bachs developer-portal endpoint, a signing secret, and selected event types. Relevant events are `collection.succeeded`, `collection.failed`, `collection.underpaid`, `payout.created`, `payout.paid`, `payout.failed`, `refund.created`, `refund.paid`, and `refund.failed`. Deliveries include `X-Bachs-Signature`; verify the raw body before parsing. The Goalmatic verifier uses timestamp plus HMAC-SHA256 over `${timestamp}.${rawBody}` with a five-minute tolerance ([client.ts](/Users/anthonyakpan/Desktop/go/gm/backend/functions/src/payments/bachs/client.ts#L269)). The local webhook additionally claims an event in `payment_webhook_events` and prevents concurrent/replayed completion (`bachsWebhook.ts:45-82`), but only for the existing billing event set.

Bachs’ [go-live requirements](https://docs.bachs.io/go-live) say verification covers the product, identity, and withdrawal account; the withdrawal account name must match the verified individual or registered company, and the sandbox-to-live transition is a key swap after approval. This is provider documentation, not proof that Goalmatic or any Allworld seller is verified. No deployment, live key, merchant account, payout destination, webhook registration, sandbox payout, or production payout was checked in this task.

## Recommendation and precise gap

Allworld sellers can plausibly use their own Paystack or Bachs path, but Bachs should be added behind a new provider-neutral seller settlement contract. Keep buyer checkout, Allworld order state, seller earnings ledger, Bachs charge/settlement metadata, withdrawal request, and terminal payout evidence as separate records. Start with same-currency NGN seller withdrawals to approved bank destinations. Require seller onboarding/eligibility, destination approval, balance/available-earnings checks, idempotent payout creation, asynchronous `payout.paid`/`payout.failed` handling, refund reconciliation, and an operations view before claiming seller funds are withdrawable. Do not include deposits, peer transfers, betting, crypto, or game-wallet conversion in this scope.

The exact missing Goalmatic work is a new Bachs seller/marketplace adapter: connected-account or merchant onboarding, account capability reads, balance reads, payout-destination management, payout create/retrieve/list, payout webhook handling, and the policy tying an Allworld seller balance to a Bachs payout. Existing Bachs source proves only Goalmatic subscription/credit/marketplace collection and refund plumbing. Deployment and provider eligibility remain unverified.
