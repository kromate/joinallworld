## Implementation order and delivery proof

Start with the existing [six-phase sequence](lagos-life-current-comparison-2026-10-09.md): reliable money/recovery, messaging, households/commissions, voluntary assets/commerce, places/courts/outings, then bounded visual nightlife. The row Unit names group work within that order; they are not new independent deadlines.

Each missing model needs authoritative types, permission/ownership checks, explicit quoted costs/expiry, once-only writes and restart/reconnect behavior before UI. Household/editing interaction compares two or three actual prototypes before committing. Extend existing controllers instead of adding duplicate clocks, assistants, policy/election systems or money effects. Preserve every current save and locked contract.

Keep each new screen/feature/asset lazy. Retain current startup/first-paint/scene/asset budgets and profile physical devices; passing byte limits alone does not prove no lag or heat. Prove keyboard/touch/320/390, visible focus, pending/error/retry and long text on the real consumer. Exact compiler/build/checks, integrated sealed Worker, provider configuration and production save/receipt continuity remain separate delivery gates.

Live app-usage ranking was not obtained: the connected PostHog tool requested reauthentication. The catalogue has consent-gated screen_view events, but a project query is needed to determine whether app-level properties exist in actual data. No measured most-used ranking, new tracking, replay/person data access or analytics configuration change is claimed.
