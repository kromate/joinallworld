# Voice-note codec and Safari compatibility notes

Checked against repository `26dbc3e1f604c3cc5442204583daf670d8ec201b` on 2026-10-09. This is a source-and-documentation review, not device testing, browser automation, or a claim that every Safari version can record and play voice notes.

## What the primary sources establish

- WebKit says Safari 18.4 added `MediaRecorder` support for producing WebM with Opus audio (and VP8/VP9 video). Apple’s Safari 18.4 release notes independently list WebM support for `MediaRecorder` and list Safari 18.4 availability across iOS 18.4, iPadOS 18.4, visionOS 2.4, macOS 15.4, Sonoma, and Ventura. This corrects the older assumption that WebKit’s WebM support was playback-only, but it does not establish support on earlier Safari/iOS releases or every device configuration. [WebKit: Safari 18.4 media features](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/), [Apple: Safari 18.4 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-18_4-release-notes)
- Safari 17’s Opus statement is specifically about macOS Sonoma playback in WebM and MPEG-4 containers. It should not be used as evidence that iOS Safari 17 can record WebM/Opus with `MediaRecorder`. [WebKit: Safari 17.0 media features](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/)
- WebKit’s 2020 `MediaRecorder` article documents Safari’s then-supported MP4/AAC recording path and recommends `MediaRecorder.isTypeSupported()` for format detection. Treat that as evidence of a historical fallback route, not a promise about current support for a particular MP4/AAC MIME string on every Safari version. [WebKit: MediaRecorder API](https://webkit.org/blog/11353/mediarecorder-api/)
- The W3C MediaStream Recording Working Draft defines `isTypeSupported()` as a capability indication, not a guarantee that a recording will finish: encoding can still fail because of runtime resource limits or other errors. It exposes the recorder’s selected `mimeType`, and records output as blobs through `dataavailable`. MDN makes the same capability-versus-runtime distinction. [W3C: MediaStream Recording Working Draft](https://www.w3.org/TR/mediastream-recording/), [MDN: `MediaRecorder.isTypeSupported()`](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/isTypeSupported_static)
- Apple’s Safari 26 release notes list ALAC and PCM recording support, while WebKit’s Safari 18.4 article already describes those formats. The release-note chronology alone therefore does not establish the first supported version for each device. Neither format matches this app’s WebM-only server contract. [Apple: Safari 26.0 release notes](https://developer.apple.com/documentation/safari-release-notes/safari-26-release-notes), [WebKit: Safari 18.4 media features](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)
- Microphone capture requires a secure context and user permission. A page embedded in a frame additionally needs microphone delegation from its top-level document through Permissions Policy; otherwise the browser need not present a prompt. A permission request may remain pending while the person makes no choice. [MDN: `getUserMedia()` security and privacy](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)
- `MediaRecorder.start(timeslice)` does not promise evenly timed chunks. MDN specifically warns that Safari may pause camera/microphone capture and delay `dataavailable`, producing larger chunks; it says not to use chunk counts to measure elapsed time. This supports treating backgrounding and interruptions as acceptance cases, but does not specify a universal current Safari background-capture guarantee. [MDN: `dataavailable` timing](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/dataavailable_event), [W3C: MediaStream Recording](https://www.w3.org/TR/mediastream-recording/)

## How this maps to the current source

The current format union contains only `webm-opus`, with MIME `audio/webm;codecs=opus`, and shared limits of 60,000 ms and 512,000 bytes in [`src/types/voice-note.ts`](../../src/types/voice-note.ts). [`voiceRecorder.ts`](../../src/app/features/messages/voiceRecorder.ts) checks that exact MIME with `MediaRecorder.isTypeSupported()`, requests mono audio after the user presses Record, starts a recorder with that MIME, caps accumulated bytes, and times the note with `performance.now()`. It stops when the page becomes hidden, releases microphone tracks, presents a local review, and has an explicit unsupported-browser/text fallback. [`VoiceComposer.vue`](../../src/app/features/messages/VoiceComposer.vue) shows a cancel control while permission is pending and distinguishes a permission denial from a generic microphone startup failure.

The server contract is narrower than “browser audio.” [`server/social/voice-notes.ts`](../../server/social/voice-notes.ts) parses and rewrites a bounded single-track WebM/Opus container, derives duration from its packets, and does not decode the audio. [`server/routes/social.ts`](../../server/routes/social.ts) accepts only data that passes this inspection and serves the stored WebM/Opus MIME type. The format tag, Node store metadata, SQLite voice rows, and Worker route all use this existing format contract. Therefore, selecting AAC/MP4 in the browser alone would fail the current upload contract; it would not be an AAC fallback implementation.

The parser’s container and packet checks are not speech recognition, content classification, or semantic audio moderation. A note passing them only means it satisfies the implemented structural and size/duration constraints. The integration handoff also records this boundary in [`docs/VOICE-NOTES-WIP.md`](../VOICE-NOTES-WIP.md).

## Acceptance still needed

1. Run a versioned real-device matrix for the supported iOS/iPadOS Safari and desktop Safari releases. For each device, capture the exact `isTypeSupported('audio/webm;codecs=opus')` result, recorder `mimeType`, final `Blob.type`, byte count, and whether the server accepts and the same device plays the uploaded recording. Safari 18.4 documentation is a reason to test WebM/Opus there; it is not test evidence for this app.
2. Exercise microphone permission grant, denial, no device, revoked permission, an unanswered permission prompt with Cancel, and the production HTTPS origin. If the app is embedded, verify the top-level Permissions Policy. Check that all stop/cancel/error paths stop every acquired track and never upload a partial or stale account/chat draft.
3. On physical iPhone/iPad, test hiding the tab, switching apps, screen lock, incoming call/audio interruption, return to the tab, and a recording near the 60-second/512,000-byte limits. Confirm the UI reports a recoverable interruption and that observed server packet duration, rather than UI timer or `timeslice` count, is authoritative. Browser emulation cannot establish these behaviors.
4. If older Safari or another target browser needs AAC/MP4, design and verify that as a complete format extension: exact supported recorder MIME selection; actual returned format verification; bounded MP4/audio-track inspection and duration derivation; consistent Node and Worker parsing/storage/read MIME; and retry, deletion, report, privacy, and restart coverage for the additional format. Do not broaden the accepted MIME type without those boundaries. The existing WebM parser cannot validate MP4, and codec/container documentation alone does not provide an AAC parser or moderation capability.

No physical-device, AAC/MP4, uninterrupted-background, semantic-moderation, or broad Safari compatibility claim is made by this note.
