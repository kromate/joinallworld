# v7 remote source/compact GPU comparison

This is a separate corrected recipe version after v1's remote controller failed its JavaScript parse. The published v1 record is preserved; this folder only addresses the duplicate Chrome log binding and keeps the same frozen v7 package and review matrix.

This is a prepared, remote-only review of the already-built v7 fixture artifact from GitHub Actions run `37888890296`, commit `e603cd25be04b350d63001b1d6ecbe2e1c82db28`. It does not change the v7 fixture, production files, or budgets. The prior run only packaged the viewer; it did **not** execute the Meshopt recipe or review pixels.

The workflow first verifies `source-snapshot.json`, downloads and verifies that exact artifact, then launches the runner's preinstalled Google Chrome in a Linux headless ANGLE SwiftShader process group under 1280 MiB RSS and a 60-second wall limit. It resolves the Chrome launcher and sibling ELF binary and records both hashes and versions. Chrome uses the single-process/in-process-GPU diagnostic topology because the normal multi-process launch exceeded this memory limit in an earlier remote run; this changes what the run can say about browser performance. CDP drives the fixture's public DOM controls and records matched source/compact captures from the same loaded actor, skeleton, normalized look, pose and camera. Actors `graphics-host-crowd-02` (man/hoodie) and `graphics-host-crowd-03` (woman/Owambe) cover both body families and two authored wardrobes. Each is captured at yaws 0° and 90° for idle, sampled walk phase 0.5, and interact in both modes: 24 matched PNGs total. Back views, sit, and continuous-motion behavior are explicitly outside this sample. The report checks the pinned candidate seed, actor identity, geometry signature, and bone-pose checkpoint at every A/B pair, records actual renderer counters and compact typed-array bytes, and hashes every PNG.

SwiftShader screenshots are diagnostic evidence only. They cannot establish hardware-GPU fidelity, mobile performance, battery use, whole-market triangle/draw budgets, or production acceptance. A human still needs to review the captured pixels and any failed states. The constrained browser process topology is especially unsuitable for performance inference.

The workflow is prepared for manual dispatch and a push only to `codex/graphics-market-lod-v7-gpu-review-v3`; it is not installed on the default branch. `source-snapshot.json` pins the review recipe files; the workflow embeds its SHA-256. The workflow is omitted from that manifest to avoid self-reference, and the manifest verifier is itself pinned by the manifest. Do not rebuild or mutate the pinned v7 fixture as part of this comparison.

Root review: the remote Chrome harness ceiling is 1280 MiB after measured startup stops at 938356736B and 861863936B. Node heap96MiB/time60s and local/mobile/game budgets remain independently enforced; this is not a mobile memory allowance or acceptance claim.

## v2 monitor race and v3 receipt behavior

The v2 run `37891411499` completed its 24-capture browser review successfully (`review-results.json` reports `success: true`) but the outer monitor failed after 28.589 seconds because `ps` briefly reported a zero-RSS owned group before the controller exit status was collected. The process group stayed below its 1280 MiB cap, cleanup succeeded, and source pins remained unchanged. The screenshots are diagnostic inputs for independent review; this wrapper race means the run is not recorded as an overall pass.

This v3 copy gives a zero/absent-RSS sample a bounded 1.25-second terminal grace. It records per-process RSS peaks and PID/state/command breadcrumbs. A completed run still requires at least one positive RSS sample; a still-live zero-RSS group after the grace remains a monitor failure. The receipt also summarizes the browser result file so a wrapper failure cannot obscure whether capture completed. Limits and the 24-capture matrix are unchanged.
