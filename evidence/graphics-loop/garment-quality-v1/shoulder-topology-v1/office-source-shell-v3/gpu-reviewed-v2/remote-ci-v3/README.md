# Remote WebGL artifact preparation — v3 single-process diagnostic

This is a separate, root-reviewed remote-run recipe. It does not change production code, release CI, fixture math, screenshots, source assets, or the v2 recipe. It reuses the exact v2 viewer, body GLBs, clip pack, and production import closure; the v3 snapshot differs only in its own frozen runner/controller and declared Chrome process topology. The v3 snapshot contains 36 pinned files. `workflow.yml` is excluded because it pins that digest.

The v2 build passed (0.271 seconds, 136,912,896-byte peak process-group RSS), but its browser process group exceeded the unchanged 768 MiB cap (938,356,736 bytes at 1.227 seconds) before page readiness or screenshots. That run produced no pixel evidence. V3 tests one resource-isolation hypothesis: launch the same runner Chrome binary and ANGLE/SwiftShader backend with `--single-process --in-process-gpu --no-zygote --renderer-process-limit=1`. These flags intentionally force an unusual single-process topology; this is a constrained shader/pixel diagnostic and cannot represent normal multiprocess Chrome memory/runtime, mobile memory, GPU performance, battery, or acceptance.

All original gates remain strict and unchanged: build uses Node 24, 96 MiB old-space, 220 MiB process-group RSS and 25 seconds; browser/controller/server/Chrome share a 768 MiB RSS and 60-second process group with TERM-then-KILL cleanup. The same actual viewer API, body/chart/topology guards, shader/network/runtime-error checks, SwiftShader backend check, and exact 12 screenshot set are required. The output names are fresh (`office-source-corner-gpu-v3-single-process-*`). Missing page/API, screenshot count, shader errors, cap/timeout, source drift, or browser failure is a failed run, not a partial pass.

The four Chrome flags and their meanings are source-checkable in Chromium's primary [content switch definitions](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/content/public/common/content_switches.cc). The fixture's custom source-corner chart and normal limitations are unchanged from v2. Even successful SwiftShader pixels would establish only that this particular software-rendered diagnostic completed and show its pixels; it would not establish mobile performance or visual acceptance.

No build, browser, test, server, workflow dispatch, push, or production integration was performed while preparing v3. Root should review the frozen files and workflow digest before publishing the dedicated branch.
