# Country-directory runtime handoff (draft for Integration)

Compatibility baseline: exact C1 and source checkpoint 2bf3cd65. The 26 queued-source count below belongs to that checkpoint; later source packets do not alter the current ten admitted foreign IDs. This is the first compatibility step toward admitting the remaining African destinations, not a permanent ten-country limit. Each subsequent admission extends the trusted manifest explicitly after its geometry, journey, save and combined-budget checks pass.

## Boundary and ownership

`src/game/cities/catalogue.ts` is the eager boundary: it imports both generated rows and every city loader. In production, its sole direct consumer is `src/game/cities/registry.ts`, which builds `CITY_CATALOGUE`, `KNOWN_CITIES`, `catalogueById` and the synchronous city predicates at module evaluation. The build owner for the generated files is `scripts/city/build-catalogue.ts`; it writes `catalogue.generated.ts`, `loaders.generated.ts` and `routes.generated.ts`. Integration owns changes to these runtime files and the generator. The directory prototype under `world/tooling/` is a source/export prototype, not a runtime dependency.

The smallest viable runtime seam is the registry. Keep Nigeria's 40 generated rows and Kaduna reserved-row filtering in the current catalogue path. Put only an explicit admission manifest for the **current ten foreign city IDs** in the eager registry surface, then load their country metadata shards through an async registry preparation API. The manifest must be generated and hash-pinned with the directories; it must state the exact admitted IDs and ISO-2 mapping. It is an allowlist, not a list of all source candidates. Runtime packaging must omit candidate-only country shards entirely. The queued 26 countries must not enter the manifest, picker, `isCityId`, route graph, or any fallback path. Do not change city admission, save/database semantics, or the protected Nigeria rows.

`src/game/cities/registry.ts` owns the split and remains authoritative. Preserve synchronous answers for membership and openness from the exact admission manifest so `isKnownCityId`, `isCityId`/`isOpenCityId`, `knownCityIds`, `registeredCityIds` and `playableCityIds` do not become speculative or async. Full metadata lookups (`cityCatalogueEntry`, `cityCatalogue`, `catalogueCitiesInState`, names, state labels and atlas positions) cannot fetch synchronously. Either ensure the relevant admitted country before a caller needs those values or make that caller's boundary async; never turn a temporarily unloaded admitted city into “unknown”, “closed”, or an invented placeholder.

## Callers to migrate or gate

- `src/app/bootstrap.ts` is already async and is the first place to prepare the saved/current city metadata before reconstruction. `src/life.ts` and `src/game/cities/lifeCities.ts` contain synchronous identity checks inside save handling; membership remains manifest-backed, while full metadata for every referenced admitted city must be prepared before any synchronous consumer uses it.
- `src/client.ts` performs synchronous destination/identity checks around async travel and content loads. Keep ID authority synchronous; ensure destination metadata before reading its name, country or position.
- `src/app/features/start/placesModel.ts` constructs `PLACES` at module load. Replace that snapshot with a post-preparation construction boundary, and ensure creator/start/find-city UI uses it only after metadata is ready.
- `src/paths.ts` builds state/city path tables from synchronous catalogue calls. Give path generation an explicit preparation point before table construction; path matching itself must remain deterministic and synchronous once prepared.
- `src/map3d/regions.ts` and `src/map3d/geo/atlas.ts` use catalogue metadata for country lists, markers, labels and generated links. Their world/atlas preparation must load the exact admitted metadata needed for that view before drawing. `src/game/cities/registry.ts` currently computes and caches generated links on the first `allCityLinks()` call, from all open cities via `generateCityLinks` in `src/game/cities/generatedLinks.ts`; Authored routes already load lazily through `loadCityLinks()`. Preserve both route results and ordering; do not describe route generation as a module-evaluation operation. If link preparation becomes async, every synchronous travel consumer must wait at an explicit startup boundary before reading `allCityLinks`/`linksFrom`.
- Direct catalogue consumers outside the registry are test-only: `src/moments/moments.test.ts` and `src/game/chatter/chatter.test.ts`. `src/app/entry.test.ts` checks generated row/loader alignment. Move assertions to the new runtime/manifest contract rather than reintroducing eager foreign rows.

## Loading, cache and failure rules

Use only manifest-selected relative shard paths and verify index/schema/hash/byte limits before exposing metadata. Do not accept a caller-provided path or infer admission from a shard's presence. Deduplicate concurrent loads by country, bound concurrent reads to two, cap the complete resident working set at 512 KiB **including index bytes**, and cap individual index/shard bytes at the verified prototype limits. Use an LRU or similarly bounded cache. Tie requests to caller abort signals, release pending entries on abort/failure/disposal, and allow a clean retry; one caller cancelling must not corrupt another caller's shared load. Reject malformed, mismatched, oversized, stale-manifest or unadmitted-city data closed. No partial city record may be published as authoritative.

The existing country-directory prototype's reader/export audit is evidence for source metadata serialization and bounded reads only. It does not prove browser cache behavior, app startup, route parity, or production delivery. Keep selection, save reconstruction and engine work behind explicit awaits; once these boundaries complete, existing synchronous engine APIs remain the authority.

## Required proof before runtime adoption

1. Assert byte-for-byte/order parity for all 40 Nigeria rows, including generated-open Kaduna shadowing the closed reserved entry exactly as `catalogue.ts` does today.
2. Assert the current ten foreign IDs and ISO mappings exactly match the pre-change admitted set. Assert all other inventory candidates, including the queued 26, remain absent from ID predicates, pickers, links and shards exposed to runtime.
3. Compare every warmed catalogue record, generated link, state grouping, route decision and map/atlas marker against the current implementation. Cover cold start, warm cache, concurrent same-country loads, two-country cap, abort, failure/retry, disposal and bad hash/schema/size/admission inputs.
4. Exercise new-life city selection and restore of existing lives with multiple referenced cities. Verify held lives, ownership, defaults, save/database payloads and Nigeria behavior are unchanged. Exercise travel/homeward links, startup, creator picker, paths and atlas before accepting the seam.
5. Record exact before/after production bundle measurements from the same release commit and same minifier/compression settings. Current candidate headroom is only **7 Brotli bytes**. Report removed eager bytes, added manifest/adapter bytes and resulting Brotli delta separately; a positive source removal is not bundle savings, and no savings claim is valid until the shipped bundle is measured. Also record first-use request bytes/latency and the cold/warm residency peak.

Integration owns all implementation, caller migration, tests and release measurement. This draft authorizes no runtime edits or admission expansion.

The candidate must also audit `warmLanding()` and other concurrent bootstrap imports before relying on one preparation await: a module-level `PLACES` or path snapshot may otherwise execute while metadata is still pending. The server must retain trusted synchronous access to all admitted destinations; browser metadata loading cannot govern server admission or fare authority. Measure the client/server split before choosing it.
