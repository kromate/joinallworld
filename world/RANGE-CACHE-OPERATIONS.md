# Exact source range cache — operations and acceptance

This is a bounded builder optimization for exact HTTP byte ranges. It does not change the Overture release, request hashes, extracts, receipts, compiler, campaign identity, or game data. The implementation is in `tooling/range_cache.py` and the existing `tooling/acquire.py` proxy. Cache entries are immutable and keyed by the pinned URL, release, file length, strong ETag, and inclusive byte span; each sidecar records the validated `206`, exact `Content-Range`, identity encoding, byte count, and SHA-256. Cache use still performs a current-process HEAD check. Partial-overlap assembly and eviction are not supported.

## Limits and next acceptance

This wave demonstrates bounded cache population and integrity, **not a cache hit**. A no-claim campaign replay reads completed extracts and therefore cannot demonstrate RangeProxy reuse. Any later savings claim must come from an audited same-identity range hit that reports its exact saved span bytes; do not infer savings from repeated Parquet URLs or aggregate cache size. The four uncoupled cache entries must remain unattributed until attempt-scoped failure telemetry can establish provenance.

The current campaign remains partial: 100/100 roots are pending, no geometry was compiled, and the four captured leaves have zero supported rows. Do not treat those facts as country coverage or playability. Keep the per-request network/disk caps, shared campaign accounting, and immutable prior products unchanged. A future bounded query wave can assess exact cache reuse under the same pinned Overture release and exact interval identities; no throughput forecast follows from this Senegal sample.

## Validation and use

The final coordinator run passes 40 Python cases (29 range/proxy cases, the original eight acquisition cases and three typed failure protocol cases). The focused Node integration passes 25 cases covering acquisition, typed failures and schema2 campaign recovery. Local fake-origin tests demonstrate an exact cross-proxy hit after a fresh HEAD, concurrent single-flight, malformed/corrupt response rejection, quotas, interruption and accounting settled before success becomes visible. They are distinct from the real wave's zero-hit evidence. Earlier failed combined runs remain retained; only `range-cache-local-tests-accepted.stderr` and `range-cache-node-integration.tap` are the accepted final runs.

Existing campaign commands enable caching automatically inside the existing release acquisition index. Retain the source release, campaign identity, limits, completed/exhausted attempts and all previously published extracts. A zero-job saved-entrypoint replay checks cached campaign products; it does not execute the range proxy. Failure attempts can retain immutable ranges, but failure-scoped range telemetry is not yet published. Do not attribute their producing requests or forecast savings from cache population.

The cache admits at most 32,000,000 total bytes, 256 entries, 8,000,000 bytes per entry and 8,000,000 new bytes per invocation, with at least 32,000,000 bytes free disk. Limits may only shrink. Existing acquisition accounting reserves growth before query execution and subtracts all admitted disk use from temporary headroom. Exact keys contain release, URL, pinned full file length, fresh strong ETag, and inclusive interval. Cache integrity errors fail closed. Full quota skips new writes; no eviction, interval assembly or old-source reset occurs.

The live Senegal checkpoint intentionally advanced from five to seven source attempts: last invocation charged 7,918,278 response bytes, 424 input/output bytes and 7,929,265 shared-cache growth bytes. Cumulative charges are 31,605,757 / 1,696 / 1,696 / 7,948,529 bytes respectively. Unchanged historical source/grid files and the copied pre-wave mutable checkpoint are pinned in `range-cache.json`. The full world remains incomplete.
